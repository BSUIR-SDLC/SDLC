# Модели динамического поведения описываются на UML текстом PlantUML и связываются идентификаторами

## Контекст и постановка задачи

Описание дизайна нужно дополнить моделью динамического поведения системы: прецедентами, диаграммами активности, состояний и последовательности. Модели должны храниться в репозитории вместе с документацией, меняться через запрос на слияние и быть связаны с требованиями SRS и представлениями SDD. Каким способом строить диаграммы и как обеспечить их связь с остальными документами?

Связанные требования: REQ-CM-001, REQ-FUNC-005 – REQ-FUNC-031 (через прецеденты). Элементы дизайна: DV-013 – DV-019.

## Драйверы решения

* Изменения диаграмм должны быть видны в истории Git построчно, как изменения текста.
* Диаграммы должны соответствовать нотации UML 2.5: актёры, включение и расширение, дорожки, сигналы, фокус управления, создание и уничтожение объектов, ограничения длительности.
* Инструмент не должен требовать платных лицензий (REQ-COMP-001).
* По любому элементу модели должно быть понятно, какое требование он реализует.

## Рассмотренные варианты

* Графический редактор (StarUML, Visual Paradigm) с файлом модели в репозитории
* Диаграммы Mermaid прямо в Markdown
* Текстовое описание UML на PlantUML с картинками PNG в репозитории

## Итог решения

Выбранный вариант: «Текстовое описание UML на PlantUML с картинками PNG в репозитории», потому что только он даёт полную нотацию UML для всех четырёх видов диаграмм и при этом хранится как текст. Mermaid не поддерживает диаграмму прецедентов, а файлы графических редакторов в Git видны как двоичные изменения.

### Механизм построения

1. Каждая диаграмма описывается в отдельном файле `uml/*.puml`. Одна диаграмма – один файл, имя файла совпадает с именем диаграммы в `@startuml`.
2. Порядок построения повторяет порядок анализа: сначала глоссарий и дополнительные спецификации, затем прецеденты и их потоки событий, затем по потокам событий строятся диаграммы активности, по сущностям с жизненным циклом – диаграммы состояний, по шагам основных потоков – диаграммы последовательности.
3. Картинки строятся командой `java -jar plantuml.jar -charset UTF-8 -tpng -o images *.puml` из каталога `uml`. Для диаграмм прецедентов и состояний используется встроенная раскладка `smetana`, поэтому Graphviz не нужен. Для диаграмм последовательности включён режим `teoz`, который поддерживает ограничения длительности.
4. Файлы PNG в `uml/images` коммитятся вместе с исходниками, поэтому GitHub показывает диаграммы в SDD без установки программ.

### Механизм связей

| Связь | Как обеспечивается |
|---|---|
| Требование SRS → прецедент | В таблице прецедентов `uml/use-cases.md` для каждого UC указаны идентификаторы REQ-FUNC |
| Прецедент → диаграммы | Идентификатор прецедента записан в заголовке диаграммы (например, AD-01 – UC-09, SD-02 – UC-05) |
| Диаграмма → SDD | Каждая диаграмма входит в своё представление DV-013 – DV-019 с разделом More Information |
| Диаграмма → ADR | Сообщения и действия на диаграммах используют имена из решений: `set_incident_status` из ADR-0003, Argon2id из ADR-0005, `Ack` и номер пачки из ADR-0002 |
| Термин → определение | Названия актёров, состояний и сообщений берутся из `uml/glossary.md` |
| Общие требования | Требования, относящиеся к нескольким прецедентам, вынесены в `uml/supplementary-specification.md` со ссылкой на номера прецедентов |

### Последствия

* Хорошо, потому что изменение диаграммы проверяется в запросе на слияние как обычный текст.
* Хорошо, потому что идентификаторы позволяют пройти от требования до диаграммы последовательности и обратно.
* Плохо, потому что после изменения `.puml` нужно не забыть пересобрать PNG, иначе картинка в SDD устареет.
* Нейтрально, потому что раскладку элементов выбирает PlantUML, и её можно менять только подсказками направления.

### Подтверждение

Перед запросом на слияние все файлы `uml/*.puml` собираются командой из пункта 3 без ошибок, а дата изменения PNG не раньше даты изменения исходника. Каждый UC из `uml/use-cases.md` встречается хотя бы в одном представлении SDD.

## Плюсы и минусы вариантов

### Графический редактор

* Хорошо, потому что раскладку можно выровнять вручную.
* Плохо, потому что файл модели двоичный или громоздкий, изменения в Git не читаются.
* Плохо, потому что удобные редакторы платные.

### Mermaid

* Хорошо, потому что GitHub рисует диаграммы сам, без картинок.
* Плохо, потому что нет диаграммы прецедентов и ограничений длительности.

### PlantUML

* Хорошо, потому что поддерживает все виды диаграмм UML, нужные для модели поведения.
* Нейтрально, потому что для сборки картинок нужна Java.

## Дополнительная информация

Диаграммы, построенные в лабораторной работе №4 на Mermaid (DV-006, DV-007, DV-012), оставлены как обзорные. Подробные модели поведения находятся в DV-013 – DV-019. Решение пересматривается, если GitHub начнёт показывать PlantUML без картинок.
