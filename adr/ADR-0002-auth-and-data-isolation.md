# Хранить серверную сессию и проверять владельца на каждом запросе

## Контекст и постановка задачи

Планер хранит личные данные аккаунтов. Требуется обеспечить вход, завершение сессии и запрет доступа к чужим записям (REQ-FUNC-001—002, REQ-FUNC-017—018, REQ-SEC-001—005). Какой механизм доступа выбрать для браузерного клиента и как гарантировать изоляцию при каждой операции?

## Драйверы решения

* Приватность записей и минимизация последствий XSS/утечки токенов.
* Простая реализация в едином Spring Boot приложении.
* Требование завершать сессию при выходе и бездействии.

## Рассмотренные варианты

* Серверная сессия с защищённой cookie.
* Самостоятельный JWT в localStorage.
* Внешний провайдер идентификации.

## Итог решения

Выбрана серверная сессия с cookie `HttpOnly`, `Secure`, `SameSite` и защитой от CSRF для изменяющих запросов. Контекст аутентификации задаёт пользователя; DAO-запросы включают `owner_id`. Пароль хранится как стойкий криптографический хеш. Срок бездействия настраивается конфигурацией.

### Последствия

* Хорошо: выход и отзыв сессии контролируются сервером.
* Хорошо: браузерный JavaScript не читает cookie.
* Плохо: для нескольких экземпляров потребуется общее хранилище сессий либо sticky sessions.
* Плохо: cookie требует CSRF защиты и корректной настройки HTTPS.

### Подтверждение

Проверить отказ анонимному запросу, доступ к своей и чужой записи, выход, истечение сессии, CSRF-защиту и отсутствие пароля в журналах.

## Плюсы и минусы вариантов

### Серверная сессия

* Хорошо: централизованный отзыв и малый объём клиентского кода.
* Плохо: сессионное хранилище нужно разделять при горизонтальном масштабировании.

### JWT в localStorage

* Хорошо: серверу проще быть stateless.
* Плохо: сложнее безопасно отзывать токен; XSS может прочитать токен.

### Внешний провайдер

* Хорошо: меньше собственного кода для восстановления доступа и MFA.
* Плохо: внешняя зависимость, стоимость и настройки не входят в согласованный MVP.

## Дополнительная информация

Реализация описана в [SDD DV-04](../sdd/planora-sdd.md). Требования восстановления доступа остаются открытым вопросом SRS; перед промышленным запуском их нужно уточнить.

## Механизмы построения и связи UML-модели

Механизм показан в [диаграмме последовательности сохранения задачи](../sdd/uml/sequence-save-task.puml) и описан в [дополнительных спецификациях](../sdd/planora-additional-specifications.md). API получает `userId` только из проверенного серверного контекста сессии. Прикладной сервис передаёт этот ID репозиторию; чтение, изменение и удаление выполняются с условием владельца. Клиент не может подменить ID владельца.

Диаграмма показывает основные исходы запроса: недействительная сессия (401), ошибка полей (400 с `fieldErrors`) и ошибка хранилища (5xx). Только подтверждённая запись переводит UI из `loading` в `success`. Ошибка сохраняет введённую форму и не создаёт ложного подтверждения. Импорт CSV повторно проверяет сессию при подтверждении и создаёт записи только для текущего владельца внутри одной транзакции; ошибка приводит к откату целиком.

| Сценарий | Контроль доступа и сохранности |
|---|---|
| Вход и выход | Защищённая cookie, серверный отзыв сессии, CSRF-контроль изменяющих запросов. |
| CRUD и поиск | Владелец берётся из сессии; фильтр `owner_id` применяется на сервере. |
| Экспорт | Выбираются только записи текущего владельца. |
| Импорт | При подтверждении проверяются сессия и токен предпросмотра; сохранение атомарное. |

Предусловия, потоки и постусловия сценариев описаны в [спецификации вариантов использования](../sdd/planora-use-cases.md).
