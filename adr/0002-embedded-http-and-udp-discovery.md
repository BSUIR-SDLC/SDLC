# ADR-0002: Встроенный HTTP/1.1 сервер на QTcpServer и UDP-автообнаружение в локальной сети

## Контекст и постановка задачи

В рамках учебной и локальной эксплуатации системы FlowerBox сервер магазина запускается на рабочем ПК флориста в локальной Wi-Fi сети. Покупатель (или тестировщик на смартфоне Android) должен подключаться к серверу без сложной настройки IP-адресов и без аренды внешнего VPS-сервера. При этом необходимо обеспечить предсказуемый REST JSON API (REQ-INT-005) и автоматическую проверку доступности сервера.

**Проблема:** как организовать сетевое взаимодействие между Android-приложением `FlowerBoxApp` и сервером `FlowerBoxServer.exe` на базе Qt 6 без сторонних сетевых библиотек и ручной настройки адресов?

## Драйверы решения

* **Простота развёртывания:** нулевая настройка сети для флориста и покупателя в локальной Wi-Fi сети.
* **Отсутствие тяжёлых зависимостей:** использование только стандартных модулей Qt 6 (`Qt6::Network`).
* **Надёжность и тестируемость (REQ-INT-005):** таймаут запросов ≤ 10 с, тестирование API в `tst_network` на `localhost` без поднятия внешних сервисов.
* **Масштабируемость до production:** протокол HTTP/1.1 JSON легко выносится за reverse-proxy (Nginx с TLS 1.2+, CON-3) без изменения клиентского кода.

## Рассмотренные варианты

* **Вариант 1:** Собственный HTTP/1.1 сервер на `QTcpServer` (порт 8080) + UDP broadcast автообнаружение на порту 45454.
* **Вариант 2:** Использование модуля `QtHttpServer` (Qt 6 Tech Preview / дополнительный компонент).
* **Вариант 3:** Бинарный TCP-протокол поверх `QTcpSocket` / `QDataStream`.

## Итог решения

Выбранный вариант: **«Встроенный HTTP/1.1 сервер на `QTcpServer` (:8080) + UDP-автопоиск (:45454)»**, потому что `QTcpServer` и `QUdpSocket` входят в базовый модуль `Qt6::Network` во всех поставках Qt 6.11, обеспечивают полный контроль над заголовками, телом JSON, кодами ответов (200/400/401/409/429) и позволяют клиенту автоматически находить сервер в локальной сети за < 2 секунды.

### Последствия

* **Хорошо**, потому что проект не зависит от опционального модуля `QtHttpServer`, которого может не быть в базовой установке MinGW/Android Qt.
* **Хорошо**, потому что стандартный HTTP/JSON удобно отлаживать (`curl`, тесты `tst_network`) и в будущем закрывать HTTPS-прокси (CON-3).
* **Хорошо**, потому что UDP-маяк (`FLOWERBOX_DISCOVER` → `FLOWERBOX_SERVER:8080`) избавляет пользователя от ввода IP-адреса вручную (ручной ввод сохранён как запасной вариант на `ServerPage.qml`).
* **Плохо**, потому что собственный HTTP-парсер поддерживает ограниченный поднабор HTTP/1.1 (без HTTP/2 и chunked transfer encoding), достаточный для REST API и отдачи изображений.

### Подтверждение

Проверяется набором интеграционных автотестов `tests/tst_network.cpp` (7/7 тестов: здоровье сервера, каталог, регистрация/вход, пересчёт цены, блокировка перебора, чат, отзывы).

## Плюсы и минусы вариантов

### Вариант 1: QTcpServer HTTP/1.1 + UDP broadcast

* **Хорошо**, потому что работает на стандартном `Qt6::Network` без дополнительных пакетов.
* **Хорошо**, потому что открытый текстовый JSON-контракт легко документируется и тестируется.
* **Плохо**, потому что требуется самостоятельная реализация разбора HTTP-запросов и маршрутизации (`src/server/HttpServer.cpp`).

### Вариант 2: QtHttpServer

* **Хорошо**, потому что меньше кода маршрутизации.
* **Плохо**, потому что требует отдельной установки компонента и имеет различия API между минорными версиями Qt 6.

### Вариант 3: Бинарный TCP (`QDataStream`)

* **Хорошо**, потому что компактный трафик.
* **Плохо**, потому что нарушает требование REST API (раздел 3.1.3 SRS), усложняет отладку и несовместим со стандартными HTTPS reverse-proxy.

## Дополнительная информация

* Затронутые требования SRS: `CON-3`, `REQ-INT-005`, `REQ-AVAIL-001`.
* Затронутые элементы SDD: `VIEW-01` (Композиция), `VIEW-03` (Интерфейсы API), `VIEW-04` (`UdpDiscoveryFlow`), `VIEW-05` (Развёртывание).
