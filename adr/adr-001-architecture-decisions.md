# Архитектурные решения для системы TourReview

## Контекст и постановка задачи

В ходе проектирования Desktop-приложения TourReview (система отзывов и рейтингов) необходимо было принять два ключевых архитектурных решения: выбрать технологию хранения данных и графический фреймворк для пользовательского интерфейса. Оба решения должны соответствовать ограничениям из SRS (раздел 2.3): работа локально без сервера, поддержка Java 17+, минимальные затраты на развёртывание.

## Драйверы решения

* Отсутствие необходимости развёртывать отдельный сервер БД (ограничение из SRS).
* Простота переноса и запуска приложения на Windows/Linux/macOS.
* Обеспечение надёжности и целостности данных (REQ-REL-001).
* Необходимость современного, отзывчивого интерфейса (REQ-INT-001).
* Поддержка разделения логики и представления (REQ-MAINT-001).

---

## Решение 1. Выбор базы данных

### Рассмотренные варианты
* PostgreSQL (серверная СУБД)
* H2 Database (встраиваемая, но требовательная к JVM)
* SQLite (файловая встроенная СУБД)

### Итог решения
Выбран вариант: **«SQLite»**, потому что он единственный удовлетворяет критерию отсечения — не требует установки сервера, хранит все данные в одном файле и имеет официальную поддержку JDBC для Java.

#### Последствия
* Хорошо, потому что пользователю не нужно устанавливать СУБД: достаточно запустить jar-файл.
* Хорошо, потому что база данных легко резервируется (копирование одного файла `.db`).
* Плохо, потому что SQLite имеет ограничения при высоких нагрузках на запись (не критично для Desktop).
* Нейтрально, потому что для работы с БД потребуется подключить JDBC-драйвер в `build.gradle`.

#### Подтверждение
Проверяется на этапе сборки: в `build.gradle` должна быть зависимость `org.xerial:sqlite-jdbc`. Код-ревью подтверждает, что слой `repository` не использует другие СУБД.

### Плюсы и минусы вариантов

#### PostgreSQL
* Хорошо, потому что поддерживает высокие нагрузки.
* Нейтрально, потому что требует знания SQL.
* Плохо, потому что требует установки сервера и настройки сети.

#### H2 Database
* Хорошо, потому что нативная поддержка Java.
* Нейтрально, потому что хранит данные в файле.
* Плохо, потому что при некорректном завершении JVM файл может повредиться.

#### SQLite
* Хорошо, потому что не требует сервера и установки.
* Хорошо, потому что данные хранятся в одном переносимом файле.
* Нейтрально, потому что требует подключения внешнего JDBC-драйвера.
* Плохо, потому что не предназначена для многопользовательской работы с высокой нагрузкой.

## Решение 2. Выбор GUI-фреймворка

### Рассмотренные варианты
* Java Swing (классический фреймворк)
* JavaFX (современный фреймворк)

### Итог решения
Выбран вариант: **«JavaFX»**, потому что он поддерживает декларативное описание интерфейса через FXML (разделяет UI и логику) и позволяет стилизовать интерфейс через CSS.

#### Последствия
* Хорошо, потому что FXML позволяет дизайнеру и разработчику работать параллельно.
* Хорошо, потому что интерфейс выглядит современнее и поддерживает анимации.
* Плохо, потому что JavaFX требует подключения дополнительных модулей (начиная с Java 11) в `build.gradle`.
* Нейтрально, потому что требует изучения FXML-разметки.

#### Подтверждение
Все UI-компоненты должны находиться в пакете `ui` и использовать JavaFX-контроллеры. В `build.gradle` должна быть подключена зависимость `org.openjfx:javafx-controls`.

### Плюсы и минусы вариантов

#### Java Swing
* Хорошо, потому что входит в стандартную JDK.
* Нейтрально, потому что использует императивное создание компонентов.
* Плохо, потому что интерфейс морально устарел и сложнее в стилизации.

#### JavaFX
* Хорошо, потому что поддерживает FXML и CSS.
* Хорошо, потому что имеет встроенные графики и анимации.
* Нейтрально, потому что требует подключения внешних зависимостей.
* Плохо, потому что не входит в стандартную сборку OpenJDK (требует настройки).
