# Выделение чистого Java-модуля `:core` без Android-зависимостей

## Контекст и постановка задачи

В Android-приложении Cheq критичная бизнес-логика — валидация чеков, денежная арифметика, проверка расхождений сумм, слияние результатов OCR, кросс-курсовые пересчёты по НБРБ, разбор структурированного JSON от Groq и расчёт прогресса бюджета — должна выполняться детерминированно и проверяться автоматическими тестами без привязки к камере, экранам и Android Runtime.

Как организовать модульную структуру Gradle-проекта Cheq, чтобы обеспечить быструю и независимую верификацию расчётов и парсеров, повторное использование доменной логики и низкую связанность с Android SDK (`REQ-REUSE-001`, `REQ-BUILD-001`, `REQ-MAINT-001`)?

## Драйверы решения

* **Тестируемость (`REQ-REUSE-001`, ISO 25010 Maintainability):** модульные тесты расчётов и разбора текста должны запускаться на стандартной JVM за секунды без эмулятора Android.
* **Точность и воспроизводимость (`REQ-FUNC-004`, `REQ-FUNC-010`, `REQ-ML-003`):** денежная арифметика и корпус синтетических чеков (`scripts/verify-receipt-corpus.ps1`) должны выполняться идентично в CLI-проверках и на устройстве.
* **Простота сборки (`REQ-BUILD-001`):** проект собирается Gradle Wrapper на JDK 17 без Android Studio и тяжёлых DI-фреймворков.
* **Ограничение сроков и состава команды:** архитектура должна быть понятной одному разработчику и легко расширяемой при подключении Junior-разработчика.

## Рассмотренные варианты

* **Вариант 1: Двухмодульный Gradle-проект (`:app` → `:core` на чистой Java 17)**
* **Вариант 2: Монолитный Android-модуль `:app` с разделением по пакетам**
* **Вариант 3: Многомодульная Clean Architecture (`:domain`, `:data`, `:network`, `:ocr`, `:app`)**

## Итог решения

Выбранный вариант: **«Двухмодульный Gradle-проект (`:app` → `:core` на чистой Java 17)»**, потому что он на уровне компилятора Gradle гарантирует отсутствие Android-зависимостей в расчётах и парсерах, обеспечивает мгновенный запуск 18 JUnit-наборов `:core` и CLI-скрипта корпуса чеков без накладных расходов на десятки интерфейсов и сборочных модулей.

### Последствия

* Хорошо, потому что компилятор физически запрещает импорт `android.*` в `com.receiptbox.core` — утечка Android-контекста в расчётное ядро невозможна.
* Хорошо, потому что модуль `:core` имеет единственную runtime-зависимость (`com.google.code.gson:2.13.1`), а его 18 JUnit-тестов (`ReceiptArithmeticTest`, `HistoricalRateTest`, `OcrTextMergerTest`, `GroqReceiptApiTest`, `NbrbRateClientTest` и др.) выполняются на JVM за доли секунды.
* Хорошо, потому что внешний CLI-скрипт `scripts/verify-receipt-corpus.ps1` переиспользует ровно те же классы `GroqConnection`, `GroqReceiptApi`, `ReceiptExtraction` и `ReceiptArithmetic`, что и APK.
* Плохо, потому что для абстрагирования Android-специфичных операций (SQLite, `ConnectivityManager`, чтение `assets/groq.key`) требуется явная передача интерфейсов (`HistoricalRateSource`, `ReceiptRefinement.Cloud`) со стороны `:app`.
* Нейтрально, потому что в `:app` используются два пространства имён (`com.waveberry.cheq` для Android-слоя и `com.receiptbox.core` для ядра), что требует аккуратного документирования в SDD.

### Подтверждение

1. Проверка `core/build.gradle`: плагин `java-library`, `sourceCompatibility = JavaVersion.VERSION_17`, единственная зависимость `api 'com.google.code.gson:2.13.1'`.
2. Автоматический запуск `./gradlew :core:test` (18 тестовых классов без Android SDK) и `./gradlew :app:testDebugUnitTest` (29 Robolectric/AndroidX тестов).
3. Код-ревью PR на отсутствие дублирования расчётной логики в пакете `com.waveberry.cheq.ui`.

## Плюсы и минусы вариантов

### Двухмодульный Gradle-проект (`:app` → `:core` на чистой Java 17)

`settings.gradle` включает `':core'` и `':app'`; `:app` подключает `implementation project(':core')`.

* Хорошо, потому что строгое соблюдение границы `REQ-REUSE-001` проверяется компилятором при каждой сборке.
* Хорошо, потому что время сборки и когнитивная нагрузка минимальны для малой команды.
* Нейтрально, потому что сетевые клиенты `GroqConnection` и `NbrbRateClient` опираются на стандартный `java.net.HttpURLConnection` без сторонних HTTP-клиентов.
* Плохо, потому что при дальнейшем росте числа экранов внутри `:app` порядок между `.ui`, `.data` и `.scan` поддерживается дисциплиной пакетов, а не компилятором.

### Монолитный Android-модуль `:app` с разделением по пакетам

Весь код размещается в одном Android-модуле `app/`.

* Хорошо, потому что не требуется настраивать второй `build.gradle`.
* Плохо, потому что любой разработчик может случайно завязать расчёты или парсер на `android.util.Log`, `android.text.TextUtils` или `Context`, нарушив `REQ-REUSE-001`.
* Плохо, потому что запуск тестов требует конфигурации Android Gradle Plugin и Robolectric даже для чистой математики.

### Многомодульная Clean Architecture (`:domain`, `:data`, `:network`, `:ocr`, `:app`)

Разделение приложения на 5+ отдельных Gradle-модулей со слоями мапперов DTO ↔ Entity ↔ Domain.

* Хорошо, потому что даёт максимальную изоляцию для большой команды (5+ разработчиков).
* Плохо, потому что резко увеличивает объём шаблонного кода (мапперы, фабрики, конфигурации Gradle) и сроки разработки без практической выгоды для проекта с 1–2 разработчиками.
* Плохо, потому что замедляет инкрементальную настройку Gradle и усложняет онбординг Junior-разработчика.
