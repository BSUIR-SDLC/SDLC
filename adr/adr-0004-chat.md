# Выбор Spring WebSocket для реализации чата

## Контекст и постановка задачи
В ходе второго раунда переговоров Заказчик запросил добавление встроенного чата для связи ученика и репетитора (REQ-FUNC-009). Требуется определить архитектурный подход, не замедляя работу основного сервиса и не срывая дедлайн.

## Драйверы решения
- Необходимость обмена сообщениями в реальном времени.
- Ограниченность бюджета (нельзя нанимать дорогих специалистов).
- Жесткий дедлайн проекта.

## Рассмотренные варианты
1. REST API с периодическим опросом (Polling).
2. Брокер сообщений (Kafka / RabbitMQ).
3. Spring WebSocket (STOMP).

## Итог решения
Выбран вариант **«Spring WebSocket (STOMP)»**. Он позволяет установить постоянное соединение, обеспечивая мгновенную доставку сообщений без задержек, при этом не требует развертывания отдельного тяжелого брокера сообщений.

## Последствия
- **Хорошо:** Чат работает быстро, встроен в текущий Spring Boot монолит. Для параллельной верстки UI на React привлечен Junior-разработчик, что позволяет уложиться в сроки.
- **Плохо:** Усложняется логика бэкенда, требуется настройка обработки обрывов соединения (reconnect).
