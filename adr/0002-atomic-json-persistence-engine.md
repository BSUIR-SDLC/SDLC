# ADR-002: Механизм локального хранения данных на базе JSON с атомарной записью

## Контекст и постановка задачи

Система «HabitFlow C++» функционирует в режиме 100% локальной изоляции (Air-gap / REQ-SEC-001) без подключения к сети Интернет или сторонним серверам. Приложению требуется долговременное хранение (персистентность) суточных отметок привычек, прогресса водного баланса, серий непрерывности (стриков) и персональных порогов пользователя (REQ-FUNC-008 / REQ-SYS-003). При этом критически важно гарантировать сохранность истории при внезапном сбое питания или аварийном завершении ОС (REQ-REL-001).

Какой формат и механизм локального хранения данных следует использовать?

## Драйверы решения

* **Надёжность и целостность (REQ-REL-001):** устойчивость к внезапным отключениям питания, исключение повреждения файла истории.
* **Автономность (REQ-SEC-001):** работа без внешних серверов СУБД и сетевых демонов.
* **Прозрачность и переносимость (REQ-PORT-001):** возможность просмотра и ручного резервного копирования данных пользователем.
* **Производительность:** время загрузки/сохранения базы данных менее 50 мс при базе до 10 000 дней.

## Рассмотренные варианты

* **Локальный файл JSON с атомарной заменой (Atomic Write)** — структурированный файл `habits_db.json`.
* **Встраиваемая реляционная СУБД SQLite** — файл базы данных SQLite3.
* **Собственный бинарный формат (Binary serialization)** — прямая запись структур данных C++ в бинарный поток.
* **Плоские текстовые файлы / INI** — хранение каждой записи в отдельном текстовом файле.

## Итог решения

Выбран вариант: **«Локальный файл JSON с атомарной заменой (Atomic Write)»**, потому что он обеспечивает достаточную производительность, читаемость человеком, нулевые накладные расходы на развёртывание СУБД и абсолютную защиту от повреждения данных благодаря шаблону «Save to Temp + Atomic Rename».

### Последствия

* **Хорошо:** Высокая надёжность: данные пишутся в `habits_db.json.tmp`, принудительно синхронизируются с диском (`FlushFileBuffers` / `fsync`), после чего атомарно заменяют целевой файл через `std::filesystem::rename`. В случае краха системы остаётся цела старая версия базы.
* **Хорошо:** Человекочитаемый формат UTF-8: пользователь может проверить свои данные в обычном текстовом редакторе.
* **Хорошо:** Лёгкость реализации экспорта в CSV и резервного копирования.
* **Плохо:** При объёме истории свыше 50 000 дней (более 100 лет непрерывных записей) полная перезапись файла при каждом сохранении может стать неэффективной. (Для персонального трекера это не критично).

### Подтверждение

Разработан автоматический тест `tests/test_atomic_write.cpp`, симулирующий прерывание процесса записи и подтверждающий целостность основного файла.

## Плюсы и минусы вариантов

### Локальный JSON с атомарной заменой

* Хорошо, потому что стандартный формат (RFC 8259), легко расширяемый новыми полями без сложных миграций схемы.
* Хорошо, потому что надёжно защищён от повреждения файловой системы при сбоях.
* Плохо, потому что требует парсинга всего документа при запуске приложения (занимает ~15 мс для 1 года данных).

### SQLite 3

* Хорошо, потому что транзакционная ACID-надёжность «из коробки» и индексация запросов.
* Плохо, потому что добавляет внешнюю зависимость и увеличивает сложность архитектуры (нужно настраивать SQL-драйверы Qt, миграции таблиц).
* Плохо, потому что бинарный файл базы нельзя легко просмотреть пользователю без спец. утилит типа sqlitebrowser.

### Собственный бинарный формат

* Хорошо, потому что минимальный размер файла и мгновенная загрузка за 1-2 мс.
* Плохо, потому что проблемы обратной совместимости при изменении полей структуры.
* Плохо, потому что нулевая переносимость между машинами с разным порядком байт (Endianness).
