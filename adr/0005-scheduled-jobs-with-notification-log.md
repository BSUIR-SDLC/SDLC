# Фоновые задачи на Spring `@Scheduled` с журналом уведомлений

## Контекст и постановка задачи

Напоминания отправляются раз в сутки в 09:00 Europe/Minsk, не более одного на событие, с повторами при сбое SMTP (REQ-FUNC-011-3, REQ-INT-003). Кроме того, ежедневно нужно загружать курсы, переносить даты списаний и проверять лимит. Приложение работает в одном экземпляре (ADR-0001), но сервер может перезапуститься в любой момент, в том числе во время рассылки.

Как запускать фоновые задачи и гарантировать, что пользователь не получит одно напоминание дважды и не останется без него?

## Драйверы решения

* не более одного уведомления на событие и канал (REQ-FUNC-011-3);
* повтор при сбое: до 3 попыток через 10 мин (REQ-INT-003);
* корректная работа после перезапуска сервера;
* минимум инфраструктуры (BG-5).

## Рассмотренные варианты

* Spring `@Scheduled` + таблица `notification_log` с уникальным ключом
* Quartz Scheduler с хранением заданий в базе данных
* Системный cron, вызывающий служебный HTTP-адрес приложения

## Итог решения

Выбранный вариант: «Spring `@Scheduled` + `notification_log`», потому что при одном экземпляре приложения кластерный планировщик не нужен, а запись события в журнал до отправки с уникальным ключом (user, subscription, kind, due_date, channel) гарантирует отсутствие дублей и даёт основу для повторов.

### Последствия

* Хорошо, потому что повторный запуск `ReminderJob` безопасен: уже записанные события пропускаются.
* Хорошо, потому что журнал уведомлений одновременно служит журналом событий для REQ-OBS-001.
* Плохо, потому что при запуске второго экземпляра приложения задачи выполнялись бы дважды (защищает только уникальный ключ); для масштабирования потребуется ShedLock.

### Подтверждение

Тест: два последовательных запуска `ReminderJob` для одного события создают одну запись и одно письмо. Тест: при ошибке канала статус `FAILED`, `RetryJob` повторяет отправку не более 3 раз.

## Плюсы и минусы вариантов

### `@Scheduled` + `notification_log`

* Хорошо, потому что встроено в Spring, без новых зависимостей.
* Хорошо, потому что идемпотентность обеспечивает база данных.
* Нейтрально, потому что расписание задаётся в коде (`cron`, `zone = "Europe/Minsk"`).

### Quartz

* Хорошо, потому что хранит задания и поддерживает кластер.
* Плохо, потому что 11 служебных таблиц и настройка ради шести задач.

### Системный cron

* Хорошо, потому что расписание вне приложения.
* Плохо, потому что нужен защищённый служебный адрес и настройка сервера вне репозитория; не работает одинаково на Windows (REQ-PORT-001).

## Дополнительная информация

SDD: 006-interaction (рисунок 3.10), 009-concurrency, 010-patterns (упрощённый transactional outbox). ADR-0007 добавляет канал Telegram к тому же журналу.

UML-модель (ЛР5, ADR-0008): задачи `@Scheduled` — это прецеденты актёра «Время» UC-20…UC-23 (рисунок 3.5 SDD). Механизм журнала показан тремя связанными диаграммами: активность [ad-3-reminders](../uml/models/ad-3-reminders.dot) — порядок действий рассылки, последовательность [sq-3-reminders](../uml/models/sq-3-reminders.mmd) — вставка записи до отправки и обработка `DuplicateKeyException`, состояния [sm-3-notification](../uml/models/sm-3-notification.dot) — жизненный цикл записи `PENDING → SENT | FAILED → UNDELIVERED`. Статус `PENDING` (запись до отправки) добавлен в модель данных по результатам моделирования, SDD 0.4.
