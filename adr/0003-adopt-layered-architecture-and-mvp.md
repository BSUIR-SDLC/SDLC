# ADR-003: Применение трёхслойной архитектуры и паттерна Model-View-Presenter (MVP)

## Контекст и постановка задачи

При разработке приложений на фреймворке Qt часто возникает антипаттерн «Smart UI» (толстый виджет), когда бизнес-логика расчёта процентов, обработки данных и файлового ввода-вывода пишется непосредственно в методах-слотах `QMainWindow`. Это приводит к сильной связанности кода, невозможности написания юнит-тестов без инициализации графической подсистемы и блокировке повторного использования математических модулей.

Какую архитектурную организацию и паттерн проектирования следует выбрать для обеспечения тестируемости, модульности и сопровождаемости системы (REQ-MAINT-001, REQ-REUSE-001)?

## Драйверы решения

* **Изолированность бизнес-логики (REQ-MAINT-001):** ядро расчёта дисциплин и стриков не должно зависеть от GUI-библиотеки Qt.
* **Тестируемость (Testability):** возможность полного покрытия ядра и персистентности модульными тестами в консольном CI/CD без подъёма графического сервера.
* **Параллельная разработка:** разделение задач между Senior (архитектура, ядро, персистентность) и Junior (верстка UI, стилизация, CSV экспорт).

## Рассмотренные варианты

* **Трёхслойная архитектура + Model-View-Presenter (Passive View)**.
* **Классический Model-View-Controller (MVC)**.
* **Монолитный двухслойный дизайн Qt (Smart Widget)**.

## Итог решения

Выбран вариант: **«Трёхслойная архитектура + Model-View-Presenter (MVP)»**, потому что он обеспечивает полное разделение ответственности: View ничего не знает о бизнес-логике, Presenter управляет потоком данных, а Model содержит чистое ядро C++17 без зависимостей от Qt.

### Последствия

* **Хорошо:** Слой предметной области (Core Domain) пишется на чистом C++17 STL (`DisciplineCalculator.hpp`, `StreakManager.hpp`) и тестируется изолированно.
* **Хорошо:** Лёгкость замены интерфейса (например, при необходимости создания консольной версии для CLI).
* **Хорошо:** Чёткое разграничение задач между разработчиками: Junior может безопасно верстать UI через интерфейс `IHabitView`, не ломая внутренние алгоритмы расчёта.
* **Плохо:** Увеличение количества промежуточных классов и интерфейсов (абстрактные классы View и Presenter).

### Подтверждение

Архитектурная проверка соблюдения инвариантов зависимостей: модуль `Core Domain` не должен содержать директив `#include <Q...>` (проверяется статическим линтером / grep в CI).

## Плюсы и минусы вариантов

### Model-View-Presenter (Passive View)

* Хорошо, потому что View максимально глупое (только отображает данные и генерирует события кликов).
* Хорошо, потому что Presenter легко покрывается Mock-тестами.
* Плохо, потому что требует написания boilerplate-кода для связывания интерфейсов.

### Классический MVC

* Нейтрально, потому что традиционен для веб-приложений.
* Плохо, потому что в MVC View напрямую подписывается на изменения модели, что в Qt Widgets приводит к размыванию ответственности и усложнению управления потоками.

### Smart Widget (Монолитный MainWindow)

* Хорошо, потому что код пишется быстрее на самых ранних стадиях прототипа.
* Плохо, потому что код превращается в «спагетти», методы UI содержат прямые SQL/JSON-вызовы, невозможно протестировать алгоритм расчёта стриков без кликов мышкой в GUI.
