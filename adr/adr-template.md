# ADR-001: Выбор фреймворка Avalonia UI для кроссплатформенной разработки

## Контекст и постановка задачи
Утилита GitPulse по требованиям SRS (REQ-CON-001) должна одинаково эффективно функционировать на операционных системах Windows, Linux и macOS. Необходимо выбрать технологию для реализации десктопного графического интерфейса на языке C#.

## Драйверы решения
* Требование абсолютной кроссплатформенности (Windows, Linux, macOS).
* Использование единого технологического стека C# / .NET 9.
* Поддержка паттерна MVVM для разделения логики и представления.
* Высокая производительность рендеринга табличных данных (DataGrid).

## Рассмотренные варианты
* WPF (Windows Presentation Foundation)
* Windows Forms
* .NET MAUI
* Avalonia UI

## Итог решения
Выбран вариант **«Avalonia UI»**, потому что это единственный кроссплатформенный .NET-фреймворк с полноценной поддержкой Linux, независимый от платформозависимых компонентов и поддерживающий декларативный UI на XAML с паттерном MVVM.

### Последствия
* Хорошо, потому что обеспечивается полная кроссплатформенность без переписывания UI под каждую ОС.
* Хорошо, потому что стандартный MVVM-подход упрощает тестирование.
* Плохо, потому что сообщество меньше, чем у классического WPF.

### Подтверждение
Проверка принятого решения осуществляется на этапе сборки проекта под целевые ОС в CI/CD конвейере.

## Плюсы и минусы вариантов

### WPF
* Хорошо, потому что зрелая экосистема в Windows.
* Плохо, потому что отсутствует нативная поддержка Linux и macOS.

### Windows Forms
* Хорошо, потому что прост в освоении.
* Плохо, потому что устаревшая архитектура и привязка только к Windows.

### .NET MAUI
* Хорошо, потому что официальный фреймворк от Microsoft.
* Плохо, потому что слабая поддержка десктопных ОС (особенно Linux).

### Avalonia UI
* Хорошо, потому что полная кроссплатформенность (Windows, Linux, macOS).
* Хорошо, потому что XAML/MVVM «из коробки».
* Нейтрально, потому что требует изучения специфики стилизации Avalonia.

# ADR-002: Использование Git CLI через дочерние процессы вместо нативных библиотек

## Контекст и постановка задачи
Необходимо считывать состояние репозитория (`Clean`/`Dirty`) и активную ветку на разных ОС без возникновения конфликтов нативных бинарных библиотек.

## Драйверы решения
* Независимость от архитектуры процессора (x64, ARM64) и ОС.
* Минимизация внешних зависимостей и сторонних NuGet-пакетов.
* Гарантия корректной работы со стандартным системным Git.

## Рассмотренные варианты
* Библиотека LibGit2Sharp
* Прямой вызов консольного процесса Git CLI (`git status`, `git branch`)

## Итог решения
Выбран вариант **«Запуск консольного процесса git»**, потому что он избавляет от проблем с кроссплатформенной сборкой нативных си-библиотек (`libgit2`) и гарантирует стабильную работу при наличии установленного Git >= 2.40.

### Последствия
* Хорошо, потому что нет проблем с нативными компиляциями под Linux и macOS.
* Плохо, потому что требуется наличие установленного в системе Git CLI.

### Подтверждение
Валидация через интеграционные тесты проверки доступности системного Git при старте приложения.

## Плюсы и минусы вариантов

### LibGit2Sharp
* Хорошо, потому что высокая скорость работы в памяти без порождения процессов.
* Плохо, потому что капризные нативные бинарники (`git2.dll` / `libgit2.so`), ломающие кроссплатформенную сборку.

### Git CLI (System Process)
* Хорошо, потому что абсолютная надежность и идентичность системному поведению Git.
* Нейтрально, потому что небольшой накладной расход на запуск процесса.

# ADR-003: Хранение результатов сканирования в оперативной памяти без СУБД

## Контекст и постановка задачи
Утилита выполняет разовый локальный аудит диска и не требует сохранения истории сканирований в персистентную базу данных между перезапусками.

## Драйверы решения
* Сохранение портативности приложения (Portable-формат без инсталлятора).
* Отсутствие необходимости миграций и обслуживания БД.
* Высокая скорость отображения данных в таблице в реальном времени.

## Рассмотренные варианты
* Встраиваемая БД SQLite
* Хранение состояния в оперативной памяти процесса (`ObservableCollection`)

## Итог решения
Выбран вариант **«Хранение в оперативной памяти»**, потому что данные о состоянии репозиториев и размере сборочного кэша быстро устаревают, а отказ от СУБД упрощает развертывание и делает утилиту полностью портативной.

### Последствия
* Хорошо, потому что приложение не создает файлов баз данных и работает прямо в памяти.
* Плохо, потому что при перезапуске приложения результаты сканирования сбрасываются.

### Подтверждение
Проверка архитектурными тестами на отсутствие обращений к локальной файловой системе для персистенции данных.

## Плюсы и минусы вариантов

### SQLite
* Хорошо, потому что позволяет сохранять историю аудитов.
* Плохо, потому что избыточно для одноразовой утилиты очистки кэша.

### In-Memory Storage
* Хорошо, потому что максимальная скорость и нулевой порог входа.
* Хорошо, потому что полная портативность.

# ADR-004: Механизмы построения и связи компонентов при сканировании и очистке

## Контекст и постановка задачи
По результатам моделирования динамического поведения (Use Case, Activity, State Machine, Sequence) и согласования приоритетов с заказчиком необходимо зафиксировать единые механизмы взаимодействия между слоями `GitPulse.UI`, `GitPulse.Core` и `GitPulse.Infrastructure`, асинхронного выполнения, защиты от удаления несохранённых изменений, обработки ошибок и логирования в `gitpulse.log` без затягивания сроков поставки.

## Драйверы решения
* Разделение ответственности между слоем представления (`MainWindow`, `MainViewModel`), прикладным слоем (`DiskScannerService`, `CleanupService`, `ThresholdChecker`) и инфраструктурным слоем (`GitCliExecutor`, `OsFileSystemProvider`, `FileLogger`).
* Единые интерфейсные контракты между слоями (`IScanningService` / `IDiskScanner`, `ICleanupService`, `IGitCliExecutor` / `IGitService`, `IFileSystemProvider`, `ILogger`) с поддержкой асинхронности и отмены через `CancellationToken`.
* Безопасная очистка сборочных артефактов (порог 500 МБ, контроль статуса `Clean`/`Dirty`, модальное подтверждение перед удалением).
* Фиксация ошибок доступа, сбоев `Git CLI (>= 2.40)` и результатов операций в `gitpulse.log` без падения всей операции.
* Реалистичное планирование работ с учётом приоритетов (`PRIO-01`..`PRIO-05`), подключения Junior-разработчика к рутинным задачам/логированию и поэтапного развития сценариев контроля кэша.

## Рассмотренные варианты
* Прямые вызовы `Git CLI` и файловой системы из `MainViewModel` с блокировкой потока UI.
* Слоистая архитектура с асинхронными сервисами через интерфейсы, явными переходами состояний (`Idle`, `Scanning`, `Ready`, `ConfirmingCleanup`, `Cleaning`, `Error`), модальным подтверждением и централизованным логированием в `gitpulse.log`.

## Итог решения
Выбран вариант **«Слоистая архитектура с асинхронными сервисами, явными состояниями, подтверждением очистки и логированием в `gitpulse.log`»**, потому что он связывает пользовательские сценарии с компонентами и внешними системами (`Git CLI >= 2.40`, файловая система ОС) через чёткие контракты и безопасно обрабатывает сбои и отмену операций.

### Последствия
* Хорошо, потому что `MainViewModel` координирует команды и состояние UI, `DiskScannerService`, `CleanupService` и `ThresholdChecker` инкапсулируют логику сканирования, очистки и проверки порога 500 МБ, а `GitCliExecutor`, `OsFileSystemProvider` и `FileLogger` изолируют работу с процессами, диском и журналом `gitpulse.log`.
* Хорошо, потому что передача `CancellationToken` и обработка исключений на уровне отдельного репозитория/каталога предотвращают зависание приложения и потерю остальных результатов.
* Хорошо, потому что подключение Junior-разработчика к вспомогательным задачам и логированию снижает риск срыва дедлайна при развитии сценариев контроля кэша.
* Плохо, потому что добавление модального подтверждения и ветвлений обработки ошибок увеличивает число сценариев для тестирования.

### Подтверждение
Проверка обеспечивается прохождением сценариев сканирования, отмены, подтверждения/отмены очистки и записи ошибок в `gitpulse.log` на тестовых каталогах с репозиториями `Clean` и `Dirty`.

## Плюсы и минусы вариантов

### Прямые вызовы из ViewModel без изоляции слоёв
* Хорошо, потому что меньше промежуточных классов и интерфейсов на старте.
* Плохо, потому что усложняет тестирование, смешивает UI-логику с работой ОС/Git и повышает риск зависания интерфейса.

### Слоистая архитектура с сервисами, состояниями и логированием
* Хорошо, потому что чётко прослеживаются связи между диаграммами поведения, компонентами и требованиями (`REQ-*`).
* Хорошо, потому что ошибки ввода-вывода и сбои `Git CLI` диагностируются по записям в `gitpulse.log`.
* Нейтрально, потому что требует согласованного ведения интерфейсов и состояний между слоями.

# ADR-005: Механизмы построения и связей компонентов приложения GitPulse

## Контекст и постановка задачи
При проектировании статической структуры GitPulse (диаграммы классов `gitpulse-classes.png`, компонентов `gitpulse-components.png` и развёртывания `gitpulse-deployment.png`) необходимо закрепить единые механизмы построения слоёв, организации интерфейсных связей между ними, контроля правил безопасности (`Clean`/`Dirty`, порог 500 МБ, модальное подтверждение, `CancellationToken`), ведения журнала `gitpulse.log` и развёртывания на рабочей станции пользователя под `.NET 9`.

## Драйверы решения
* Чёткое разделение ответственности между слоями `GitPulse.UI`, `GitPulse.Core` и `GitPulse.Infrastructure` без циклических зависимостей.
* Связывание компонентов через интерфейсные контракты (`IScanningService` / `IDiskScanner`, `ICleanupService`, `IGitCliExecutor` / `IGitService`, `IFileSystemProvider`, `ILogger`) с внедрением зависимостей (DI) для сервисов и адаптеров (`DiskScannerService`, `CleanupService`, `ThresholdChecker`, `GitCliExecutor`, `OsFileSystemProvider`, `FileLogger`).
* Защита пользовательских данных: блокировка выбора репозиториев со статусом `Dirty`, расчёт суммарного объёма артефактов (`bin`, `obj`, `node_modules`) относительно порога 500 МБ и обязательное модальное подтверждение перед удалением.
* Устойчивость к ошибкам доступа, сбоям внешнего `Git CLI (>= 2.40)` и отмене операций по `CancellationToken` с фиксацией событий в `gitpulse.log`.
* Кроссплатформенная поставка в виде архива `GitPulse.zip` (Portable / Self-contained) для Windows, Linux и macOS на базе `.NET 9` / Avalonia UI.

## Рассмотренные варианты
* Прямая связность классов и вызовов ОС внутри единого модуля без чётких интерфейсных границ между слоями.
* Слоистая компонентная модель (`GitPulse.UI` -> `GitPulse.Core` -> `GitPulse.Infrastructure`) с интерфейсными контрактами, проверкой статуса/порога/отмены, записью в `gitpulse.log` и манифестацией сборок `GitPulse.UI.dll`, `GitPulse.Core.dll`, `GitPulse.Infrastructure.dll` при развёртывании.

## Итог решения
Выбран вариант **«Слоистая компонентная модель с интерфейсными контрактами, защитой очистки, логированием в `gitpulse.log` и манифестацией сборок»**, потому что он задаёт прозрачные точки интеграции между компонентами, изолирует системные вызовы и обеспечивает переносимость приложения.

### Последствия
* Хорошо, потому что `GitPulse.UI` (`MainWindow`, `MainViewModel`) работает только с прикладными сервисами через `IScanningService` / `IDiskScanner` и `ICleanupService`, не зная деталей запуска `git` или обхода файловой системы.
* Хорошо, потому что `GitPulse.Core` (`DiskScannerService`, `CleanupService`, `ThresholdChecker`) инкапсулирует бизнес-логику проверки статуса `Clean`/`Dirty` и порога 500 МБ, а `GitPulse.Infrastructure` (`GitCliExecutor`, `OsFileSystemProvider`, `FileLogger`) реализует контракты `IGitCliExecutor` / `IGitService`, `IFileSystemProvider` и `ILogger` для работы с `Git CLI >= 2.40`, каталогами и `gitpulse.log`.
* Хорошо, потому что на диаграмме развёртывания сборки `GitPulse.UI.dll`, `GitPulse.Core.dll` и `GitPulse.Infrastructure.dll` явно соотнесены (`<<manifest>>`) с архитектурными компонентами внутри портативного пакета `GitPulse.zip`.
* Плохо, потому что поддержание единых имён контрактов и моделей между диаграммами классов, компонентов, развёртывания и кодом требует аккуратной синхронизации при рефакторинге.

### Подтверждение
Согласованность проверяется сопоставлением диаграмм классов, компонентов и развёртывания с разделами SDD, прохождением сценариев сканирования/очистки с `Clean`- и `Dirty`-репозиториями и проверкой записей в `gitpulse.log`.

## Плюсы и минусы вариантов

### Прямая связность без интерфейсных границ
* Хорошо, потому что меньше интерфейсов и прослоек на раннем этапе.
* Плохо, потому что усиливается связанность слоёв, усложняется подмена зависимостей при тестировании и выше риск ошибок при работе с файловой системой и `Git CLI`.

### Слоистая компонентная модель с контрактами и манифестацией сборок
* Хорошо, потому что направления зависимостей и внешние точки интеграции (`Git CLI >= 2.40`, локальные каталоги, `gitpulse.log`) однозначно читаются на всех статических диаграммах.
* Хорошо, потому что логика безопасности (порог 500 МБ, запрет очистки `Dirty`, отмена и журнал ошибок) встроена в архитектуру компонентов.
* Нейтрально, потому что требует внимания к единой терминологии во всех проектных документах.
