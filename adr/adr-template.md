# ADR-001: Выбор встроенной СУБД SQLite в режиме WAL для локального хранения финансовых данных

## Контекст и постановка задачи

Десктопная система персонального финансового учета **FinanceTracker (Java)** предназначена для ведения семейного и личного бюджета с повышенными требованиями к конфиденциальности (REQ-SEC-001) и полной автономности без подключения к сети Интернет (REQ-AVAIL-001). При этом система должна гарантировать сохранность транзакций при аварийном отключении питания (REQ-REL-001) и обеспечивать время отклика интерфейса не более 200 мс при объеме базы до 100 000 записей (REQ-PERF-001).

Какую систему хранения данных следует выбрать для десктопного Java-приложения, чтобы обеспечить нулевое администрирование на стороне пользователя, ACID-надежность и высокую скорость аналитических выборок?

## Драйверы решения

- **Полная автономность и локальность данных (REQ-SEC-001, REQ-AVAIL-001):** все финансовые записи должны храниться исключительно на диске пользователя в одном переносимом файле без сетевых запросов.
- **Надежность и целостность транзакций (REQ-REL-001):** гарантия соблюдения требований ACID и защита от повреждения файла БД при внезапном завершении процесса.
- **Производительность (REQ-PERF-001):** время выполнения агрегирующих SQL-запросов (подсчет баланса, группировка по категориям для JavaFX Charts) должно составлять менее 50 мс на 100 000 записей.
- **Простота развертывания (REQ-PORT-001):** отсутствие необходимости устанавливать и настраивать отдельные серверные службы на ОС Windows, Linux и macOS.
- **Бюджет и сроки итерации (SDD, SYS-01):** на проектирование ядра БД и DAO-слоя выделено 16 часов (2 рабочих дня).

## Рассмотренные варианты

- Вариант 1: Встроенная реляционная СУБД SQLite (режим WAL + драйвер sqlite-jdbc)
- Вариант 2: Встроенная Java-СУБД H2 Database
- Вариант 3: Клиент-серверная СУБД PostgreSQL
- Вариант 4: Сериализация данных в локальные JSON / CSV файлы

## Итог решения

Выбранный вариант: **«Вариант 1: Встроенная реляционная СУБД SQLite (режим WAL + драйвер sqlite-jdbc)»**, потому что это единственный вариант, обеспечивающий одновременно нулевое администрирование (один компактный файл `finance.db`), полноценную поддержку реляционных SQL-запросов с индексами для быстрой аналитики, ACID-надежность через журнал упреждающей записи (WAL) и независимость от формата JVM при резервном копировании.

### Последствия

- **Хорошо, потому что** база данных представляет собой единый локальный файл (`finance.db`), который пользователь может легко скопировать или перенести на другой ПК без установки СУБД.
- **Хорошо, потому что** режим `PRAGMA journal_mode=WAL;` и `PRAGMA foreign_keys=ON;` обеспечивает высокую скорость чтения/записи и строгую ссылочную целостность между таблицами `categories` и `transactions`.
- **Хорошо, потому что** хранение сумм в целочисленном формате `INTEGER` (в копейках/центах) в связке с `java.math.BigDecimal` в Java полностью исключает ошибки округления валют (`BYN`, `USD`, `EUR`).
- **Плохо, потому что** SQLite не поддерживает одновременную сетевую запись с нескольких рабочих станций (приемлемый компромисс для однопользовательского десктопного приложения).
- **Плохо, потому что** в SQLite отсутствует встроенный тип `DECIMAL`, что обязывает DAO-слой (`TransactionDao`) выполнять конвертацию `amount_cents <-> BigDecimal`.

### Подтверждение

Соблюдение данного решения проверяется на этапе проектирования и реализации следующими способами:
1. Код-ревью конфигурации `SqliteConnectionManager` (обязательное выполнение `PRAGMA journal_mode=WAL;` и `PRAGMA foreign_keys=ON;` при инициализации соединения).
2. Модульные и интеграционные тесты (`BalanceCalcTest.java`, `CrashRecoveryTest.java`, `ResponseTimeTest.java` из раздела 4 SRS), подтверждающие корректность транзакций и время выборки < 200 мс на тестовом наборе из 100 000 записей.

## Плюсы и минусы вариантов

### Вариант 1: Встроенная реляционная СУБД SQLite (режим WAL + драйвер sqlite-jdbc)

Реляционная встраиваемая БД на языке C, подключаемая к Java SE 17+ через стандартный JDBC-драйвер `org.xerial:sqlite-jdbc`.

- **Хорошо, потому что** не требует установки отдельного сервера и фоновых служб ОС (удовлетворяет REQ-PORT-001).
- **Хорошо, потому что** обеспечивает полную поддержку SQL-индексов, `GROUP BY` и оконных функций для модуля аналитики `SYS-08` (удовлетворяет REQ-PERF-001).
- **Хорошо, потому что** файл БД имеет открытый стандартизированный бинарный формат, независимый от версии Java.
- **Нейтрально, потому что** требует подключения одной внешней зависимости (`sqlite-jdbc`) в сборке Maven/Gradle.
- **Плохо, потому что** блокирует файл на запись при параллельных пишущих потоках (решается использованием пула с одним пишущим соединением).

### Вариант 2: Встроенная Java-СУБД H2 Database

Легковесная СУБД, написанная полностью на Java, работающая во встроенном (embedded) режиме.

- **Хорошо, потому что** нативно интегрируется в JVM без платформозависимых бинарных библиотек.
- **Хорошо, потому что** поддерживает стандартные типы данных SQL, включая `DECIMAL(19, 2)`.
- **Нейтрально, потому что** также хранит данные в локальном файле на диске пользователя.
- **Плохо, потому что** формат файла БД H2 чувствителен к мажорным обновлениям версии движка (риск несовместимости при миграции версий приложения).
- **Плохо, потому что** потребляет больше оперативной памяти JVM по сравнению с нативной библиотекой SQLite.

### Вариант 3: Клиент-серверная СУБД PostgreSQL

Полнофункциональная объектно-реляционная клиент-серверная СУБД.

- **Хорошо, потому что** обладает максимальной масштабируемостью, строгой типизацией (`NUMERIC`) и отказоустойчивостью.
- **Нейтрально, потому что** отлично поддерживается в Java через стандартный драйвер JDBC.
- **Плохо, потому что** требует предварительной установки, настройки и постоянного запуска серверного демона на компьютере обычного пользователя (нарушает принцип автономности и простоты установки).
- **Плохо, потому что** избыточна для локального персонального трекера финансов.

### Вариант 4: Сериализация данных в локальные JSON / CSV файлы

Хранение всего реестра операций в текстовом файле на диске с полной загрузкой в оперативную память при старте.

- **Хорошо, потому что** не требует СУБД и JDBC-драйверов, максимальная простота на малых объемах (до 500 записей).
- **Нейтрально, потому что** данные легко читаются человеком в любом текстовом редакторе.
- **Плохо, потому что** при каждом добавлении или удалении транзакции требуется перезаписывать весь файл целиком, что при сбое питания ведет к потере всех данных (нарушает REQ-REL-001).
- **Плохо, потому что** деградирует по скорости поиска и агрегации при росте истории до 50 000 – 100 000 записей (нарушает REQ-PERF-001).

## Дополнительная информация

- **Связанные артефакты:** требования SRS (`REQ-FUNC-001..005`, `REQ-PERF-001`, `REQ-SEC-001`, `REQ-REL-001`, `REQ-AVAIL-001`), архитектурное описание слоя доступа к данным в `sdd/sdd-template.md` (модули `SYS-01`, `SYS-02`, `SYS-08a`).
- **Согласование:** решение принято Архитектором системы (Богдан М. А.) и согласовано с Заказчиком в рамках лабораторной работы № 4 по дисциплине «Жизненный цикл разработки программного обеспечения» (БГУИР, 2026).
- **Условия пересмотра:** решение подлежит пересмотру только в случае изменения бизнес-требований и перехода от локального однопользовательского приложения к многопользовательской облачной клиент-серверной архитектуре.

# ADR-002: Динамическое взаимодействие слоёв UI, Service и DAO в FinanceTracker

* **status:** accepted
* **date:** 2026-11-27
* **decision-makers:** Богдан М. А. (Архитектор / Lead Java Developer)

## Контекст и решение
Для обеспечения тестируемости, точности финансовых расчётов и времени отклика < 200 мс зафиксировано строгое однонаправленное взаимодействие слоёв: `Presentation (JavaFX / MVVM) -> Service (валидация BigDecimal, расчёт баланса, CSV) -> DAO (SQLite WAL)`. Удаление транзакций защищено обязательным модальным подтверждением на уровне UI и журналированием в `finance_app.log`.
