# ADR-001: Выбор реляционной СУБД PostgreSQL для транзакционного учета квот билетов

## Контекст и постановка задачи

Система «EventPulse» оперирует финансовыми показателями продаж и ограниченными пулами физических мест на мероприятиях (категории «VIP» и «Стандарт»). Критической бизнес-проблемой является риск параллельной покупки последних доступных билетов разными пользователями (состояние гонки / Race Condition), что ведет к перепродаже мест (овербукингу), финансовым штрафам и репутационным убыткам организатора. 

Как обеспечить строгую целостность финансовых транзакций, атомарный учет остатка квот и предотвратить овербукинг при высокой конкурентной нагрузке, сохраняя удобство аналитических запросов для сводной таблицы продаж?

## Драйверы решения

- **Транзакционная надежность (ACID)**: гарантия недопустимости перепродажи билетов сверх установленной физической вместимости зала (требования BR-1, NFR-02, SR-SEC-01).
- **Сложная агрегация аналитики**: необходимость выполнения быстрых расчетов суммарной выручки и заполняемости залов по формулам в реальном времени (FR-RPT-01, BR-5).
- **Контроль бизнес-правил на уровне БД**: декларативные ограничения целостности (CHECK-констрейнты на неотрицательные цены и сумму квот).
- **Сроки и простота сопровождения**: минимизация времени команды на разработку собственного слоя управления распределенными блокировками.

## Рассмотренные варианты

- **PostgreSQL** (Реляционная объектно-ориентированная СУБД)
- **MongoDB** (Документоориентированная NoSQL СУБД)
- **In-Memory хранилище Redis** (в качестве единственной основной базы данных)

## Итог решения

Выбранный вариант: **PostgreSQL**, потому что данная СУБД из коробки предоставляет надежный механизм транзакционной изоляции (уровни `Read Committed` и `Serializable`), поддерживает строчные пессимистические блокировки (`SELECT ... FOR UPDATE`), декларативные ограничения целостности данных (CHECK constraints, Foreign Keys) и зрелый диалект SQL для мгновенной агрегации отчетов по продажам.

### Последствия

- **Хорошо**: Полное устранение риска овербукинга благодаря блокировке строк в момент оформления заказа.
- **Хорошо**: Высокая скорость генерации сводной таблицы продаж за счет реляционных индексов по внешним ключам `event_id` и встроенных функций агрегации (`SUM`, `COUNT`).
- **Хорошо**: Гарантия соблюдения бизнес-правил (например, `total_capacity >= SUM(quota)` и `price_vip >= price_standard`) на уровне ядра БД.
- **Нейтрально**: Требуется поддержка миграций схемы данных при добавлении новых сущностей (например, промокодов).
- **Плохо**: Сложнее выполнять горизонтальное масштабирование на запись (sharding) по сравнению с документоориентированными NoSQL-системами, однако в рамках объема Backoffice-панели организатора текущей производительности одиночного узла PostgreSQL достаточно с многократным запасом.

### Подтверждение

Соблюдение решения подтверждается:
1. Интеграционными стресс-тестами конкурентного списания квот (симуляция 50 параллельных запросов на покупку последних 5 мест с проверкой исключения перепродажи).
2. Наличием миграций с CHECK-ограничениями в репозитории проекта.
3. Прохождением код-ревью архитектурных решений при мердже Pull Request в ветку `main`.

## Плюсы и минусы вариантов

### PostgreSQL

Реляционная СУБД общего назначения с открытым исходным кодом и мощным механизмом транзакций.

- **Хорошо**: Строгое соответствие критериям ACID и поддержка блокировок строк на уровне транзакций.
- **Хорошо**: Развитая экосистема ORM-библиотек и инструментов администрирования (pgAdmin 4).
- **Хорошо**: Богатые возможности индексации (B-Tree индексы по датам и внешним ключам).
- **Плохо**: Строгая схема требует написания формальных скриптов миграций при модификации таблиц.

### MongoDB

Популярная документоориентированная СУБД, хранящая данные в формате JSON-подобных документов (BSON).

- **Хорошо**: Гибкая схема документа, позволяющая легко менять структуру полей события.
- **Хорошо**: Быстрая запись простых изолированных документов.
- **Плохо**: Отсутствие декларативных связей между таблицами; расчет аналитики и сводных отчетов требует сложных конвейеров агрегации (Aggregation Pipeline).
- **Плохо**: Многодокументные транзакции обладают меньшей производительностью и сложнее настраиваются для предотвращения гонок остатков квот.

### Redis (как основное хранилище)

Быстрая база данных в оперативной памяти (Key-Value / In-Memory).

- **Хорошо**: Экстремальная скорость отклика (субмиллисекундные задержки).
- **Хорошо**: Наличие атомарных счетчиков (`DECRBY`) для квот.
- **Плохо**: Высокий риск потери данных при сбоях питания без персистентных дампов.
- **Плохо**: Непригодна для сложных реляционных выборок, фильтрации и построения сводных аналитических таблиц организатора.

## Дополнительная информация

- Решение принято и согласовано в рамках Раунда 1 ролевой игры с Заказчиком.
- Связанные требования: SRS (`FR-TCK-03`, `BR-1`, `BR-4`, `NFR-02`), SDD (`VIEW-003: TransactionQuotaManager`).
- Пересмотр решения возможен только в случае трансформации закрытой аналитической панели Backoffice в высоконагруженную глобальную платформу продажи билетов с потоком более 100 000 транзакций в секунду.

# ADR-002: Применение паттерна «Конечный автомат» (State Pattern) для управления статусами мероприятия

* **status:** "accepted"
* **date:** 2026-11-12
* **decision-makers:** "Чурик М.В. (Архитектор / Senior Fullstack разработчик)"

## Контекст и постановка задачи
Мероприятие в системе EventPulse проходит через несколько этапов жизненного цикла (черновик, активные продажи, полная распродажа билетов, отмена, завершение). Неконтролируемое изменение статусов или прямое удаление активного события с проданными билетами приводит к потере финансовой отчётности и нарушению прав покупателей. Как гарантировать строгую валидность переходов между состояниями и защитить данные от некорректного удаления?

## Рассмотренные варианты
* **Реализация конечного автомата (State Pattern) на уровне бизнес-логики и БД**
* **Свободное изменение строкового поля `status` через обычный `UPDATE`-запрос**

## Итог решения
Выбран вариант **реализации конечного автомата (State Pattern)** в соответствии с построенной UML-диаграммой состояний (`docs/uml/state-machine.png`), потому что он жёстко инкапсулирует правила переходов (Guard Conditions):
* Физическое удаление (`deleteDraft`) разрешено исключительно из состояния `Draft` при `sold_count == 0`.
* Перевод в состояние `Cancelled` при `sold_count > 0` автоматически запускает процедуру возврата средств (`initRefunds()`) и архивацию записи вместо её удаления.
