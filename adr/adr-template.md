# ADR-001: Выбор фреймворка Avalonia UI для кроссплатформенного интерфейса PassVault

## Контекст и постановка задачи
Менеджер паролей **PassVault** по требованиям SRS должен обеспечивать единообразный десктопный интерфейс на операционных системах Windows и Linux[cite: 4, 13]. Необходимо выбрать технологию графического интерфейса на платформе .NET с поддержкой разделения логики и представления.

## Драйверы решения
* Кроссплатформенная работа на Linux и Windows без переписывания UI[cite: 13].
* Единый стек .NET / C# для десктопной утилиты[cite: 13].
* Поддержка паттерна MVVM и привязки данных (`DataBinding`)[cite: 13].
* Удобная работа с таблицами учётных записей, панелями категорий и модальными диалогами[cite: 5, 13].

## Рассмотренные варианты
* WPF (Windows Presentation Foundation)[cite: 13, 23]
* Windows Forms[cite: 13, 23]
* .NET MAUI[cite: 13, 23]
* Avalonia UI[cite: 13, 23]

## Итог решения
Выбран вариант **«Avalonia UI»**, потому что это зрелый .NET-фреймворк с нативной поддержкой Linux и Windows, декларативным XAML и паттерном MVVM[cite: 13, 23].

### Последствия
* Хорошо, потому что один кодовый базис интерфейса работает на Linux и Windows[cite: 13, 23].
* Хорошо, потому что MVVM отделяет `MainViewModel` от элементов окна и упрощает тестирование[cite: 13, 23].
* Плохо, потому что меньшая распространённость готовых сторонних тем по сравнению с WPF[cite: 23].

### Подтверждение
Проверка осуществляется сборкой и запуском проекта под целевые десктопные ОС и ревью архитектуры UI-слоя[cite: 13, 23].

## Плюсы и минусы вариантов

### WPF
* Хорошо, потому что богатая экосистема на Windows[cite: 23].
* Плохо, потому что работает только под Windows[cite: 13, 23].

### Windows Forms
* Хорошо, потому что простой старт[cite: 23].
* Плохо, потому что привязан к Windows и менее гибок для современного MVVM-интерфейса[cite: 13, 23].

### .NET MAUI
* Хорошо, потому что единый подход Microsoft для кроссплатформенных приложений[cite: 23].
* Плохо, потому что слабая поддержка десктопного Linux[cite: 13, 23].

### Avalonia UI
* Хорошо, потому что полноценная поддержка Linux и Windows[cite: 13, 23].
* Хорошо, потому что XAML и MVVM доступны «из коробки»[cite: 13, 23].
* Нейтрально, потому что требуется аккуратная настройка стилей и фокуса при автоблокировке[cite: 8, 23].

# ADR-002: Использование AES-256-GCM с PBKDF2-HMAC-SHA256 для локального шифрования сейфа

## Контекст и постановка задачи
Учётные записи и пароли в **PassVault** хранятся локально[cite: 4, 8]. Требуется защитить содержимое хранилища от несанкционированного чтения и подмены файла на диске по стандарту AES-256 на основе мастер-пароля пользователя[cite: 4, 8].

## Драйверы решения
* Строгое соответствие требованию локального шифрования AES-256[cite: 4, 8].
* Устойчивость ключа к подбору по мастер-паролю за счёт ключевой функции формирования ключа (KDF).
* Контроль целостности и аутентичности зашифрованных данных.
* Использование проверенных стандартных криптографических библиотек платформы.

## Рассмотренные варианты
* Хранение данных в открытом виде / простое кодирование
* AES-256 в режиме CBC с отдельным HMAC
* AES-256 в режиме GCM с деривацией ключа через PBKDF2-HMAC-SHA256

## Итог решения
Выбран вариант **«AES-256 в режиме GCM с деривацией ключа через PBKDF2-HMAC-SHA256»**, потому что он обеспечивает стойкое шифрование AES-256, проверку целостности контейнера и защиту ключа мастер-пароля с индивидуальной солью для каждого сейфа[cite: 4, 8].

### Последствия
* Хорошо, потому что при повреждении или изменении зашифрованного файла целостность не пройдёт проверку[cite: 8].
* Хорошо, потому что для каждого сейфа генерируется уникальная соль и одноразовый nonce.
* Плохо, потому что при потере мастер-пароля расшифровать хранилище невозможно.
* Плохо, потому что параметры KDF добавляют небольшую задержку при открытии сейфа.

### Подтверждение
Проверка выполняется модульными тестами шифрования/дешифрования, проверкой отказа при неверном мастер-пароле и код-ревью `Aes256CryptoProvider`.

## Плюсы и минусы вариантов

### Хранение в открытом виде / кодирование
* Хорошо, потому что простота реализации.
* Плохо, потому что неприемлемо для хранения паролей и учётных данных[cite: 4].

### AES-256-CBC + HMAC
* Хорошо, потому что распространённый криптографический подход.
* Плохо, потому что требует ручной сборки двух этапов и аккуратного разбора формата пакета.

### AES-256-GCM + PBKDF2-HMAC-SHA256
* Хорошо, потому что шифрование AES-256 и контроль целостности объединены в стандартном примитиве[cite: 4, 8].
* Нейтрально, потому что требует строгого управления солью и nonce для каждой записи/файла.

# ADR-003: Локальный зашифрованный файл сейфа и очистка памяти/буфера при Auto-Lock

## Контекст и постановка задачи
**PassVault** должен работать автономно без внешних серверов и защищать секреты пользователя при оставлении рабочего места без присмотра[cite: 4, 8]. Необходимо определить способ хранения сейфа и поведение системы при неактивности пользователя[cite: 4, 8].

## Драйверы решения
* Полная автономность и отсутствие зависимости от внешних баз данных или облака[cite: 4, 13].
* Минимизация времени нахождения расшифрованных паролей в оперативной памяти и буфере обмена[cite: 8, 9].
* Быстрая работа с категориями и записями в открытом сеансе[cite: 5].

## Рассмотренные варианты
* Внешняя или серверная база данных с сетевым доступом
* Локальный зашифрованный файл сейфа с оперативной очисткой при блокировке (`Auto-Lock`)

## Итог решения
Выбран вариант **«Локальный зашифрованный файл сейфа с оперативной очисткой при блокировке (`Auto-Lock`)»**, потому что он сохраняет локальную автономность[cite: 4] и автоматически блокирует интерфейс, очищает расшифрованные данные в памяти и сбрасывает буфер обмена при простое пользователя[cite: 8, 9].

### Последствия
* Хорошо, потому что все данные остаются локально под защитой AES-256 и блокируются при бездействии[cite: 4, 8].
* Хорошо, потому что при блокировке сеанса скрываются чувствительные поля и очищается буфер обмена[cite: 6, 8, 9].
* Плохо, потому что требуется резервная копия файла сейфа на стороне пользователя при переносе на другое устройство.

### Подтверждение
Проверка срабатывания таймера `IAutoLockService`, скрытия паролей маской `[****]`, очистки коллекции записей и буфера обмена при блокировке[cite: 6, 8, 9].

## Плюсы и минусы вариантов

### Внешняя / серверная БД
* Хорошо, потому что централизованное хранение.
* Плохо, потому что противоречит принципу локального безопасного хранилища и усложняет архитектуру[cite: 4].

### Локальный файл сейфа + Auto-Lock
* Хорошо, потому что простота, автономность и защита при неактивности[cite: 4, 8].
* Хорошо, потому что нет необходимости поднимать отдельные службы[cite: 4].
