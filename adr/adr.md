# Architectural Decision Record (ADR)

## ADR-001: Architecture and Storage Selection for Freelancer Cabinet (ЛР №4)

### Status
Accepted

### Context
Необходимо обеспечить надежный учет статусов заказов и запретить выплату вознаграждения без загруженного артефакта работы. На текущем этапе разрабатывается прототип в виде CLI-приложения.

### Decision
1. Архитектура: Модульная с четким разделением (UI -> Сервисный слой -> Хранилище).
2. Стек технологий: C++17, стандартная библиотека STL (vector, map, string).
3. Управление состояниями: Использование enum class TaskStatus для строгой фиксации этапов задачи.
4. Валидация сдачи: Запрет перехода в статус оплаты при отсутствии зафиксированного пути к файлу.

### Consequences
* Плюсы: Простота сборки через MinGW, отсутствие внешних тяжелых зависимостей, защита от несанкционированного начисления средств.
* Минусы: Данные хранятся в оперативной памяти (персистентная БД SQLite планируется на следующих этапах).

## ADR-002: Моделирование динамического поведения на UML (ЛР №5)

### Status
Accepted

### Context
Для формализации сценариев взаимодействия пользователя с системой и переходов состояний задачи требуется единый стандарт визуального и текстового моделирования.

### Decision
Выбран текстовый формат PlantUML (UML 2.5) для версионирования диаграмм в Git. На диаграмме Use Case применены связи ассоциации, `<<include>>` (обязательная валидация файла перед оплатой) и `<<extend>>` (опциональный отзыв заказчика).

### Consequences
* Плюсы: Диаграммы хранятся как код и легко отслеживаются в Pull Request.
* Минусы: Требуется внешний рендеринг для получения растровых изображений PNG.

## ADR-003: Моделирование статической структуры и обоснование UML-связей (ЛР №6)

### Status
Accepted

### Context
Для перехода от поведенческих моделей (ЛР №5) к устойчивой объектно-ориентированной архитектуре необходимо зафиксировать статическую структуру классов, модульные границы компонентов и схему физического развёртывания приложения.

### Decision
1. **Связи на диаграмме классов**:
   - **Композиция (`*--`)** между `FreelancerCabinet` и `Task` / `Transaction`: жизненный цикл задач и логов транзакций полностью управляется контейнером кабинета; при уничтожении объекта кабинета связанные сущности также удаляются.
   - **Реализация интерфейса (`..|>`)** между `DeliverableValidator` и `IPaymentValidator`: позволяет изолировать правила проверки сдачи файлов и при необходимости заменить валидатор без переписывания бизнес-логики.
   - **Агрегация (`o--`)** между `FreelancerCabinet` и `IPaymentValidator`: валидатор подключается к кабинету как независимый сервис.
   - **Ассоциация (`-->`)** между `Task` и `TaskStatus`: каждая задача хранит текущее состояние конечного автомата.
2. **Диаграмма компонентов**: применена компонентная декомпозиция с явным выделением предоставляемых (provided) и требуемых (required) интерфейсов (`ITaskService`, `IFileCheck`, `IPaymentService`), что снижает связность модулей (Low Coupling).
3. **Диаграмма развёртывания**: приложение поставляется как единый нативный артефакт `freelancer_cabinet.exe` в среде выполнения `MSYS2 MinGW64` на узле рабочей станции пользователя (Windows), взаимодействующий с локальной файловой системой для экспорта отчёта по транзакциям.

### Consequences
* Плюсы: прозрачная структура кода, соответствие принципам SOLID (инверсия зависимостей через `IPaymentValidator`), простота развёртывания без установки СУБД или веб-сервера.
* Минусы: локальное хранение отчётов ограничивает многопользовательскую работу без добавления сетевого узла в будущих итерациях.
