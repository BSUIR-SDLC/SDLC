# Серверная генерация страниц на Thymeleaf вместо React

## Контекст и постановка задачи

В замечании 6 к pull request SRS v0.2 напарник предложил делать интерфейс на React. Замечание было отклонено для SRS как проектное и перенесено в ADR (Приложение В SRS). Требования к интерфейсу (REQ-INT-001, мокапы 1–6) описывают формы, таблицы и диаграммы без сложного взаимодействия на клиенте.

Какую технологию интерфейса выбрать, чтобы выполнить REQ-INT-001 в срок одним разработчиком и не ослабить безопасность (REQ-SEC-001…003)?

## Драйверы решения

* трудоёмкость и срок (план: 190 ч на всё приложение);
* защита форм и сеансов (CSRF, REQ-SEC-003);
* требования REQ-INT-001: адаптивность 360–1920 px, доступ с клавиатуры, WCAG 2.1 AA;
* диаграммы аналитики (REQ-FUNC-014) и подсказки каталога (REQ-FUNC-020).

## Рассмотренные варианты

* Thymeleaf + Chart.js
* React SPA + REST API
* Thymeleaf + htmx

## Итог решения

Выбранный вариант: «Thymeleaf + Chart.js», потому что он не требует отдельного клиентского приложения и REST API, использует встроенную в Spring Security защиту форм и сеансов и покрывает все экраны мокапов; интерактивные элементы (диаграммы, подсказки) реализуются небольшими скриптами.

### Последствия

* Хорошо, потому что одна сборка Maven, без Node.js в конвейере и без второго набора тестов.
* Хорошо, потому что формы с проверкой на сервере и шаблон PRG работают без JavaScript.
* Плохо, потому что каждое действие перезагружает страницу; для отметки использования это заметно (компенсируется небольшим `fetch`-запросом без перезагрузки).
* Нейтрально, потому что при появлении мобильного клиента потребуется REST API — модули сервисов для этого уже отделены от контроллеров.

### Подтверждение

На показе итерации 1 Заказчику демонстрируется общий макет и меню (REQ-INT-001); проверка доступности — Lighthouse (оценка Accessibility не ниже 90) в итерации 5.

## Плюсы и минусы вариантов

### Thymeleaf + Chart.js

* Хорошо, потому что страницы формируются сервером, данные не дублируются в API.
* Хорошо, потому что CSRF-токены вставляются в формы автоматически.
* Плохо, потому что сложная клиентская логика была бы неудобна (в SubScope её нет).

### React SPA + REST API

* Хорошо, потому что богатый интерфейс без перезагрузок и готовность к мобильному клиенту.
* Плохо, потому что нужен REST API для всех 20 с лишним действий, отдельная сборка и тесты клиента — по оценке +35–40 ч, что не помещается в план.
* Плохо, потому что аутентификацию и CSRF для SPA приходится настраивать отдельно.

### Thymeleaf + htmx

* Хорошо, потому что частичное обновление страниц без своего JavaScript.
* Нейтрально, потому что выигрыш заметен только на отметке использования.
* Плохо, потому что ещё одна библиотека, незнакомая junior.
