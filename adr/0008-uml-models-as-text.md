# UML-модели хранятся как текст: Graphviz DOT для графовых диаграмм и Mermaid для диаграмм последовательности

## Контекст и постановка задачи

В ЛР5 проект дополняется моделью динамического поведения на UML: 4 диаграммы прецедентов, 4 диаграммы активности, 3 диаграммы состояний и 5 диаграмм последовательности (папка [uml/](../uml/README.md)). Диаграммы входят в SDD (представления 001, 006, 007, 008) и будут меняться в каждой итерации вместе с кодом: при появлении нового сценария, при изменении статусов или сообщений между модулями.

Модели должны храниться в Git, изменяться через pull request (REQ-CM-001), строиться бесплатными средствами под Windows и Linux (REQ-COST-001, REQ-PORT-001) и давать изображения, одинаковые у всех участников. Как описывать UML-диаграммы, чтобы они не расходились ни с кодом, ни друг с другом?

## Драйверы решения

* модель читается и сравнивается в pull request построчно — рецензент видит, какой переход или сообщение изменилось;
* изображение строится командой из модели, а не рисуется вручную (одна модель — одно изображение);
* поддерживаются все четыре вида диаграмм ЛР5, включая фрагменты `alt`/`opt`/`loop`, составные состояния и ортогональные регионы;
* инструменты уже есть в проекте или ставятся одной командой; без лицензий и без регистрации во внешних сервисах;
* документы на GitHub читаются без сборки.

## Рассмотренные варианты

* PlantUML
* Graphviz DOT для диаграмм прецедентов, активности и состояний + Mermaid для диаграмм последовательности
* Графический редактор (draw.io, StarUML) с хранением файлов редактора и экспортированных PNG

## Итог решения

Выбранный вариант: «Graphviz DOT + Mermaid», потому что Graphviz уже используется в SDD (контекст, модули, данные, развёртывание) и даёт полный контроль над формой узлов, нужной для UML (овалы прецедентов, дорожки, полосы разветвления, составные состояния через кластеры), а Mermaid строит диаграммы последовательности с активациями и комбинированными фрагментами, которых в Graphviz нет, и отображается GitHub без сборки. PlantUML покрыл бы всё одним языком, но требует отдельного Java-архива PlantUML вне Maven-проекта приложения (его версию нужно скачивать и обновлять вручную у каждого участника) или внешнего сервера отрисовки; выигрыш от одного языка не перевешивает второй набор инструментов рядом с уже используемым Graphviz.

### Последствия

* Хорошо, потому что каждая диаграмма — небольшой текстовый файл (`uml/models/*.dot`, `*.mmd`), изменения видны в diff pull request.
* Хорошо, потому что изображения строит один скрипт `python uml/tools/uml.py`; в репозитории хранятся и модели, и PNG, поэтому SDD читается на GitHub и в отчётах без установки инструментов.
* Хорошо, потому что идентификаторы (UC-NN, имена классов 003-logical, статусы из 004-information) пишутся в моделях текстом и проверяются поиском по репозиторию.
* Нейтрально, потому что в DOT нет готовых UML-фигур: актёр и событие времени — значки `actor.png` и `hourglass.png`, составные состояния и дорожки — кластеры; соглашения записаны в разделе «Механизм построения».
* Плохо, потому что используются два языка, а Mermaid требует Node.js и браузер Chromium (через mermaid-cli); для разработчика без Node.js изменение диаграммы последовательности сводится к правке текста, а PNG перестраивает тот, у кого инструмент есть.

### Подтверждение

Ревью pull request: изменённая модель и её PNG входят в один коммит; `python uml/tools/uml.py` не меняет файлы в `uml/images/` (изображения соответствуют моделям). Каждая диаграмма ссылается на прецеденты (UC-NN) в комментарии первой строки модели, а каждый прецедент с диаграммой указан в матрице связей [uml/README.md](../uml/README.md).

## Плюсы и минусы вариантов

### PlantUML

* Хорошо, потому что один язык для всех видов UML-диаграмм, нотация близка к стандарту.
* Нейтрально, потому что для диаграмм, кроме последовательности, сам вызывает Graphviz.
* Плохо, потому что нужен отдельный JAR-файл PlantUML вне Maven-проекта приложения или внешний сервер отрисовки, которому передаётся текст модели.

### Graphviz DOT + Mermaid

* Хорошо, потому что Graphviz уже в проекте (sdd/tools/diagrams.py), Mermaid отображается GitHub.
* Хорошо, потому что оба инструмента бесплатны и работают на Windows и Linux.
* Плохо, потому что UML-обозначения в DOT собираются из примитивов, а раскладку графа иногда приходится направлять портами и невидимыми рёбрами.

### Графический редактор

* Хорошо, потому что можно точно расположить элементы.
* Плохо, потому что изменения в двоичном или XML-файле редактора нечитаемы в pull request, а экспорт PNG легко забыть — изображение расходится с моделью.

## Дополнительная информация

### Механизм построения

1. **Источник требований.** Каждый прецедент выведен из функциональных требований SRS; трассируемость REQ → UC — [uml/use-cases.md](../uml/use-cases.md), раздел 5. Требования, общие для многих прецедентов, вынесены в [дополнительные спецификации](../uml/supplementary-specification.md), термины — в [глоссарий](../uml/glossary.md).
2. **Прецеденты.** Модель начинается с перечня событий внешнего мира; для каждого события определяется актёр-инициатор и прецедент. Повторяющееся поведение выносится во включаемый прецедент (`«include»`: UC-24, UC-25), необязательное — в расширение с точкой расширения (`«extend»`: UC-26, UC-27, UC-07). Диаграммы группируют прецеденты по функциям SRS 2.2.
3. **Активность.** Для прецедента с ветвлениями основной поток становится цепочкой действий, альтернативные потоки — ветвями решений со стражами, участники — дорожками. Параллельные независимые шаги изображаются разветвлением и соединением, обработка коллекции — областью расширения «iterative».
4. **Последовательность.** Шаги потока событий раскладываются на сообщения между объектами классов 003-logical; альтернативные потоки становятся фрагментами `alt`, расширения и необязательные шаги — `opt`, повторы — `loop`.
5. **Состояния.** Для объектов, поведение которых зависит от истории (подписка, учётная запись, запись журнала уведомлений), сообщения диаграмм последовательности и события времени становятся переходами `событие [страж] / действие`; состояния соответствуют значениям статусов в таблицах 004-information.
6. **Построение изображений.** `uml/tools/uml.py` вызывает `dot` для `*.dot` (рабочий каталог — `uml/models`, чтобы находились значки) и mermaid-cli для `*.mmd` (оформление — `uml/models/mermaid-config.json`) и сохраняет PNG в `uml/images` с тем же именем. Префикс имени модели задаёт вид диаграммы: `uc-` прецеденты, `ad-` активность, `sm-` состояния, `sq-` последовательность.

### Связи между диаграммами

Связи держатся на общих идентификаторах: номер прецедента указан в комментарии модели и в подписи рисунка SDD; имена участников диаграмм последовательности совпадают с классами 003-logical; названия состояний совпадают со статусами в базе данных (`ACTIVE`, `PAUSED`, `CANCELLED`, `PENDING`, `SENT`, `FAILED`, `UNDELIVERED`); стражи переходов повторяют условия альтернативных потоков. Полная матрица «прецедент → активность → последовательность → состояния» — в [uml/README.md](../uml/README.md).

При моделировании найдены два пробела дизайна SDD 0.3, исправленные в версии 0.4: нет хранения прошедших списаний для аналитики (таблица `charge`, UC-12, UC-22) и нет состояния записи журнала до отправки (статусы `PENDING`, `UNDELIVERED`, UC-25, ADR-0005).

SDD: 001-context, 006-interaction, 007-algorithm, 008-state, приложение А. Связанные решения: ADR-0004…0007 (их сценарии показаны на диаграммах sq-3…sq-5, ad-3, sm-3).
