# Схема PostgreSQL ведётся миграциями Flyway

## Контекст и постановка задачи

Данные хранятся в PostgreSQL (CON-3). Схема меняется почти в каждой итерации: в плане v3 добавляются таблицы курсов, отметок, журнала уведомлений, поля лимита и Telegram. После показа инкремента 1 на сервере появятся данные Заказчика, которые нельзя терять при обновлении.

Как изменять схему базы данных так, чтобы обновление было воспроизводимым на ноутбуке разработчика, в CI и на сервере?

## Драйверы решения

* сохранность данных при обновлениях (REQ-AVAIL-001);
* одинаковая схема в тестах (Testcontainers) и на сервере (REQ-MAINT-001);
* обновление одной командой (REQ-INST-001);
* простота для junior.

## Рассмотренные варианты

* Flyway (миграции на SQL)
* Liquibase (журнал изменений XML/YAML)
* `spring.jpa.hibernate.ddl-auto=update`

## Итог решения

Выбранный вариант: «Flyway», потому что миграции пишутся на обычном SQL (включая CHECK и `UNIQUE NULLS NOT DISTINCT`), хранятся в Git рядом с кодом и применяются автоматически при запуске приложения.

### Последствия

* Хорошо, потому что история схемы видна в pull request так же, как изменения кода.
* Хорошо, потому что начальный справочник категорий загружается миграцией (решение первого раунда, письмо 3).
* Плохо, потому что ошибочную применённую миграцию нельзя изменить — только исправить новой.

### Подтверждение

`spring.jpa.hibernate.ddl-auto=validate`: приложение не запускается, если сущности JPA не совпадают со схемой после миграций. Интеграционные тесты запускают все миграции на чистой базе.

## Плюсы и минусы вариантов

### Flyway

* Хорошо, потому что SQL знаком любому разработчику и позволяет использовать возможности PostgreSQL.
* Хорошо, потому что встроен в Spring Boot.
* Нейтрально, потому что откат выполняется восстановлением резервной копии, а не командой.

### Liquibase

* Хорошо, потому что поддерживает откат и независимость от СУБД.
* Плохо, потому что формат XML/YAML менее нагляден, а независимость от СУБД не нужна (CON-3).

### `ddl-auto=update`

* Хорошо, потому что не требует писать миграции.
* Плохо, потому что не удаляет и не переименовывает столбцы, не создаёт CHECK-ограничения и может незаметно расходиться с ожиданиями — недопустимо для данных на сервере.
