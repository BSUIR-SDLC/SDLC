# ADR-0005: Трёхслойная архитектура клиента (чистое C++17 ядро, Qt-модели, декларативный QML UI)

## Контекст и постановка задачи

Мобильное приложение FlowerBox включает 21 экран QML, нетривиальную бизнес-логику (конструктор букета с правилами бумаги `max(2, ceil(stems/5))`, совместимость коробок S/M/L/XL, генерация мозаики «вид сверху», расчёт скидок и бесплатной доставки от 100 BYN, валидация всех полей ввода) и требует параллельной работы двух разработчиков (архитектора/middle и подключаемого junior-разработчика) в рамках сжатых сроков.

**Проблема:** как разделить ответственность между UI и бизнес-логикой в Qt Quick приложении, чтобы обеспечить высокую скорость тестирования, производительность предпросмотра (≤ 200 мс) и безопасное распараллеливание задач между разработчиками?

## Драйверы решения

* **Тестируемость:** бизнес-правила должны проверяться быстрыми юнит-тестами (`Qt Test`) без запуска GUI и эмулятора Android.
* **Производительность (REQ-PERF-001):** перерисовка мозаики конструктора должна занимать < 200 мс даже на бюджетных смартфонах.
* **Параллельная разработка (План v3):** junior-разработчик должен иметь возможность верстать экраны QML и писать тесты, не ломая ядро расчётов.
* **Сопровождаемость (REQ-FUNC-017):** единые правила валидации для всех форм ввода.

## Рассмотренные варианты

* **Вариант 1:** Трёхслойная архитектура MVVM/MVC: чистое C++17 ядро (`src/core`) → Qt-модели (`src/models`, `QObject`/`QAbstractListModel`) → декларативный QML UI (`qml/`).
* **Вариант 2:** Реализация бизнес-логики и расчётов напрямую на JavaScript внутри QML-файлов.
* **Вариант 3:** Построение интерфейса на `Qt Widgets` (как в ЛР №1).

## Итог решения

Выбранный вариант: **«Трёхслойная архитектура: `src/core` (C++17) + `src/models` (Qt) + `qml/` (Qt Quick)»**, потому что она строго изолирует предметную логику от визуального слоя, позволяет переиспользовать `src/core` на сервере и в автотестах, обеспечивает мгновенный (< 5 мс) расчёт координат мозаики на C++ и позволяет junior-разработчику безопасно работать в папке `qml/` по фиксированным контрактам `Q_PROPERTY` и `Q_INVOKABLE`.

### Последствия

* **Хорошо**, потому что модули `src/core` (`Pricing`, `Packaging`, `BouquetLayout`, `Validation`) покрываются быстрыми юнит-тестами `tst_packaging` и `tst_shop` без GUI.
* **Хорошо**, потому что QML остаётся чистым декларативным слоем с плавными анимациями (включая живую карусель из 5 вкладок `BottomCarousel.qml`, REQ-INT-002).
* **Хорошо**, потому что задачи чётко разделяются между основным разработчиком (`src/core`, `src/net`, `src/server`) и junior-разработчиком (`qml/pages/`, `qml/components/`, юнит-тесты).
* **Плохо**, потому что добавление нового поля в модель требует обновления C++ заголовка (`Q_PROPERTY`) и пересборки, а не только правки QML.

### Подтверждение

Проверяется структурой каталогов (`src/core/` не включает `<QQuickItem>` или QML-заголовки), инспекцией кода при PR-ревью и запуском `tst_packaging` и `tst_shop`.

## Плюсы и минусы вариантов

### Вариант 1: C++17 Core + Qt Models + QML UI

* **Хорошо**, потому что высокая производительность, строгая типизация C++17 и переиспользование ядра на сервере.
* **Хорошо**, потому что чёткие границы ответственности для командной работы.
* **Плохо**, потому что немного больше связующего кода (`Q_PROPERTY`, `QAbstractListModel`).

### Вариант 2: Бизнес-логика на JS внутри QML

* **Хорошо**, потому что быстрый старт прототипирования.
* **Плохо**, потому что логику нельзя переиспользовать на C++ сервере и сложно покрывать модульными тестами.

### Вариант 3: Qt Widgets

* **Хорошо**, потому что привычный императивный C++ для десктопа.
* **Плохо**, потому что плохо адаптируется к мобильному сенсорному UX Android, свайпам и живой карусели (REQ-INT-002).
