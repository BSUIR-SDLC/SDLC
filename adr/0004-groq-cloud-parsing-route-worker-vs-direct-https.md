# Маршрут облачного разбора чеков через Groq (`openai/gpt-oss-20b`, strict JSON Schema): Cloudflare Worker против прямого HTTPS

## Контекст и постановка задачи

После локального OCR приложение Cheq извлекает структурированные позиции, магазин, дату, валюту и суффикс карты плательщика с помощью языковой модели `openai/gpt-oss-20b` в режиме строгого `json_schema` (Groq API), дополняя ответ детерминированной постобработкой `ReceiptExtraction.reconcile()` и независимой проверкой арифметики `ReceiptArithmetic` (`REQ-INT-005`, `REQ-FUNC-004`, `REQ-ML-001`).

В SRS v1.2 (по исходникам 0.9.0) зафиксированы два возможных маршрута доступа к Groq: **через прокси Cloudflare Worker** (скрывает API-ключ Groq на сервере, но требует +16 ч на разработку, деплой и сопровождение Worker и всё равно хранит клиентский токен в APK) либо **прямой HTTPS-запрос** на `https://api.groq.com/openai/v1/chat/completions` с ключом, встраиваемым в `assets/groq.key` на этапе сборки (учебная демонстрационная поставка, `REQ-DIST-001`).

Какой маршрут обращения к Groq утвердить для релиза 1.0 в рамках согласованных сроков и бюджета проекта?

## Драйверы решения

* **Сроки и стоимость (`F-06`):** добавление, тестирование, деплой и поддержка Cloudflare Worker увеличивает оценку `F-06` на 16 часов ($400) — с 44 ч до 60 ч.
* **Безопасность и честность границ (`REQ-SEC-003`, `REQ-DIST-001`, `BG-05`):** передача строго по HTTPS (`cleartextTrafficPermitted="false"`), без фотографий и `cardId`; любой секрет внутри APK (будь то ключ Groq или клиентский токен Worker) принципиально извлекаем, поэтому учебный APK не является публичной коммерческой поставкой.
* **Детерминизм и защита от галлюцинаций LLM (`REQ-FUNC-004`, `REQ-ML-002`):** модель работает с `temperature=0`, строгой JSON-схемой, запретом на следование инструкциям внутри OCR-текста (prompt injection guard), независимой арифметической проверкой и обязательным подтверждением человеком.
* **Независимость от дополнительной инфраструктуры (`REQ-COST-001`, `REQ-AVAIL-001`):** отсутствие собственного бэкенда снижает число точек отказа и эксплуатационных затрат.

## Рассмотренные варианты

* **Вариант 1: Прямой HTTPS-доступ к Groq API с ключом сборки (`assets/groq.key`) и strict JSON Schema**
* **Вариант 2: Проксирование запросов через Cloudflare Worker с клиентским токеном**
* **Вариант 3: Полностью локальный регулярный парсер чеков без LLM**

## Итог решения

Предлагаемый вариант на согласование с Заказчиком (статус `proposed`, переходит в `accepted` по итогам Раунда 1): **«Прямой HTTPS-доступ к Groq API с ключом сборки (`assets/groq.key`) и strict JSON Schema»**, при этом в первичном плане v1 заложен расширенный вариант с Worker (`F-06` = 60 ч) для прозрачного выбора Заказчиком. Отказ от Worker экономит **16 ч ($400)**, полностью устраняет необходимость поддерживать внешний сервер и соответствует фактической кодовой базе Cheq 1.0 (`GroqClient.java`, `GroqConnection.java`, `app/build.gradle`), где ключ исключён из Git (`GroqApi.key` в `.gitignore`).

### Последствия

* Хорошо, потому что экономится 16 ч разработки и устраняется отдельный инфраструктурный узел (деплой, мониторинг и продление аккаунта Cloudflare).
* Хорошо, потому что сборка без `GroqApi.key` продолжает успешно собираться (`REQ-BUILD-001`), оставляя ручной ввод, архив и статистику полностью работоспособными (`REQ-COST-001`).
* Хорошо, потому что строгие защитные барьеры в `:core` (`GroqReceiptApi`, `GroqConnection` с лимитом 256 КБ и дедлайном 55 с, `ReceiptExtraction.reconcile()`, `GroqClient.verifyCardLastFour()`, `ReceiptArithmetic`) одинаково работают независимо от сетевого маршрута.
* Плохо, потому что встроенный в учебный APK ключ Groq технически может быть извлечён путём реверс-инжиниринга (риск явно документирован в `REQ-DIST-001` и `README.md`, публикация в Google Play с таким ключом запрещена).
* Плохо, потому что при необходимости сменить провайдера или отозвать ключ потребуется пересборка APK.

### Подтверждение

1. Инспекция `app/build.gradle` (задача `prepareGroqKey`, валидация формата `gsk_[A-Za-z0-9_-]+`), `res/xml/network_security_config.xml` (`cleartextTrafficPermitted="false"`), `GroqConnection.java` (только HTTPS URL, `setInstanceFollowRedirects(false)`, таймаут 55 с, лимит 256 КБ).
2. Инспекция `.gitignore` — `GroqApi.key` не попадает в Git-репозиторий.
3. Модульные тесты `GroqReceiptApiTest`, `GroqConnectionTest`, `GroqErrorsTest`, `GroqReviewTest`, `GroqTransferTest`, `GroqCardLastFourTest`, `SteamReceiptReviewTest`, `ReceiptDiversityTest` и скрипт `scripts/verify-receipt-corpus.ps1`.

## Плюсы и минусы вариантов

### Прямой HTTPS-доступ к Groq API

`GroqClient` читает ключ из `assets/groq.key`, `GroqConnection` отправляет HTTPS POST на `https://api.groq.com/openai/v1/chat/completions`.

* Хорошо, потому что экономит 16 ч разработки (44 ч вместо 60 ч) и обнуляет затраты на хостинг прокси.
* Хорошо, потому что меньше задержка сети (нет лишнего хопа) и меньше точек отказа.
* Плохо, потому что подходит только для учебной/личной поставки; для публичного распространения потребуется серверная прослойка с пользовательской аутентификацией и rate-limiting.

### Проксирование через Cloudflare Worker

Android-клиент шлёт запросы на Worker с клиентским токеном; Worker добавляет серверный `GROQ_API_KEY`.

* Хорошо, потому что позволяет ротировать ключ Groq без обновления APK и ограничивать квоты на стороне edge-сервера.
* Нейтрально, потому что клиентский токен в APK также остаётся извлекаемым без системы пользовательских аккаунтов.
* Плохо, потому что требует +16 ч на разработку/тестирование/деплой Worker, усложняет воспроизводимость учебного проекта и вводит зависимость от ещё одного облачного провайдера.

### Полностью локальный регулярный парсер без LLM

Извлечение товаров только регулярными выражениями (`ReceiptParser`, `BankReceiptParser`, `DigitalReceiptParser`).

* Хорошо, потому что нулевая стоимость API и 100% офлайн-работа.
* Плохо, потому что не справляется с многообразием форматов кассовых чеков, сокращений, многострочных скидок и цифровых писем (`REQ-ML-001` прямо закрепляет `openai/gpt-oss-20b` как основной парсер товаров).
