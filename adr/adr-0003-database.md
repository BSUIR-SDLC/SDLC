# Выбор PostgreSQL для базы данных

## Контекст и постановка задачи
Требуется хранить данные о пользователях, профилях репетиторов, бронированиях и отзывах. Важно обеспечить строгую целостность данных (например, чтобы бронирование не могло ссылаться на несуществующего репетитора).

## Драйверы решения
- Полная поддержка ACID-транзакций.
- Надежность и устойчивость к сбоям.
- Бесплатная лицензия и открытый исходный код.

## Рассмотренные варианты
1. MySQL
2. MongoDB (NoSQL)
3. PostgreSQL

## Итог решения
Выбрана реляционная СУБД **PostgreSQL**.

## Последствия
- **Хорошо**, потому что PostgreSQL гарантирует целостность данных (ACID) и отлично подходит для сложных реляционных связей (Users -> Bookings -> Reviews).
- **Плохо**, потому что требует чуть большего администрирования по сравнению с простыми NoSQL решениями.

## Подтверждение
Проверка осуществляется через запуск интеграционных тестов и миграций (Flyway или Liquibase).

## Плюсы и минусы вариантов
- **MySQL:** Хорошо (популярность, скорость чтения), Плохо (исторически менее строгая поддержка сложных типов данных, чем в PostgreSQL).
- **MongoDB:** Хорошо (гибкая схема), Плохо (отсутствие строгих транзакций на уровне ядра исторически, сложнее обеспечивать связи между таблицами).
- **PostgreSQL:** Хорошо (строгий ACID, поддержка JSONB, расширяемость), Плохо (может быть избыточной для совсем маленьких проектов).
