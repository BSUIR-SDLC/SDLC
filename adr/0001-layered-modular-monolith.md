# ADR-0001. Модульный монолит из модулей Maven со слоями «интерфейс – сервисы – хранилище»

## Контекст и постановка задачи

GameShelf – настольное приложение на Java 21 и JavaFX 21 (ограничение C-1 SRS), которое разрабатывает один исполнитель. REQ-MAINT-001 требует, чтобы логика статусов и учёта времени не зависела от JavaFX и была покрыта тестами не менее чем на 80 %, а раздел 3.5.5 SRS – чтобы модули `timetracking` и `integration` можно было переиспользовать. Вопрос: как разделить код, чтобы эти требования выполнялись автоматически, а не держались на дисциплине разработчика?

## Драйверы решения

* REQ-MAINT-001: логика тестируется без интерфейса, покрытие ≥ 80 %
* Раздел 3.5.5 SRS: повторное использование `timetracking` и `integration`
* Один разработчик – минимум инфраструктуры и накладных расходов
* Возможность выдать junior-разработчику изолированный модуль

## Рассмотренные варианты

* Один модуль Maven с пакетами по слоям
* Модульный монолит: несколько модулей Maven, зависимости только сверху вниз
* Плагинная архитектура (ServiceLoader для всех модулей)

## Итог решения

Выбранный вариант: «Модульный монолит: несколько модулей Maven, зависимости только сверху вниз», потому что он единственный обеспечивает требования REQ-MAINT-001 и раздела 3.5.5 средствами сборки, оставаясь простым для одного разработчика.

### Последствия

* Хорошо, потому что правила статусов и времени тестируются без запуска интерфейса
* Хорошо, потому что во втором раунде это позволило передать junior-разработчику модули `library` (платформы) и `integration` (RAWG)
* Плохо, потому что каждая новая зависимость между модулями требует правки `pom.xml`

### Подтверждение

Плагин Maven Enforcer в сборке `mvn verify` запрещает модулям `progress` и `timetracking` зависеть от `org.openjfx`; нарушение ломает сборку в GitHub Actions (REQ-BUILD-001).

## Плюсы и минусы вариантов

### Один модуль Maven с пакетами по слоям

Все классы в одном артефакте, слои различаются только пакетами.

* Хорошо, потому что проект проще всего начать
* Плохо, потому что ничто не мешает импортировать JavaFX в логику статусов
* Плохо, потому что переиспользовать `timetracking` отдельно невозможно

### Модульный монолит: несколько модулей Maven, зависимости только сверху вниз

Один процесс, но модули `ui`, `library`, `progress`, `timetracking`, `stats`, `integration`, `storage`, `platform` собираются отдельно.

* Хорошо, потому что запрещённую зависимость не пропустит компилятор
* Хорошо, потому что модуль можно отдать другому разработчику с понятной границей
* Нейтрально, потому что сборка описывается в нескольких `pom.xml`

### Плагинная архитектура (ServiceLoader для всех модулей)

Модули подключаются во время выполнения через интерфейсы.

* Хорошо, потому что максимально гибко
* Плохо, потому что для однопользовательского приложения это избыточно и усложняет отладку
