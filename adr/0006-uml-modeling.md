# Моделирование динамического поведения на UML в текстовом виде

## Контекст и постановка задачи

Для ЛР5 нужно описать динамическое поведение системы «EasyTicket» на UML: прецеденты, активность, состояния и последовательность (SDD, `docs/use-cases.md`, `docs/uml.md`). Какой способ описания выбрать, чтобы диаграммы хранились вместе с кодом, проверялись в Pull Request и оставались согласованными с требованиями SRS и решениями ADR?

## Драйверы решения

* Диаграммы должны храниться в репозитории и версионироваться вместе с документами
* Изменения диаграмм должны быть видны в diff Pull Request
* Отображение прямо на GitHub без установки специальных программ
* Согласованность между диаграммами: единые имена состояний, сообщений и прецедентов
* Малый размер команды и ограниченное время

## Рассмотренные варианты

* Mermaid для активности, состояний и последовательности и PlantUML-текст для вариантов использования
* PlantUML для всех диаграмм
* Графический редактор (draw.io, Rational Rose)

## Итог решения

Выбранный вариант: «Mermaid для активности, состояний и последовательности и PlantUML-текст для вариантов использования», потому что Mermaid отображается GitHub нативно и даёт читаемый diff, а Mermaid не поддерживает диаграмму вариантов использования, для которой используется текст PlantUML (`uml/src/usecase.puml`).

### Механизм построения и связи между диаграммами

Диаграммы строятся последовательно, каждая следующая уточняет предыдущую:

1. **Вариант использования → диаграмма активности.** Основной и альтернативные потоки прецедента (шаги, ветвления «если – иначе», ошибки) переносятся в узлы действий, решений и конечные узлы активности. Один прецедент (или цепочка UC-03 → UC-04 → UC-05) даёт одну диаграмму активности.
2. **Диаграмма активности → диаграммы состояний.** Объекты, чьи атрибуты меняются в действиях активности (место, билет), описываются автоматами; события переходов совпадают с названиями действий активности (`AddToCart`, `PaymentConfirmed`, `Refund`), а защитные условия — с ромбами решений.
3. **Активность и состояния → диаграмма последовательности.** Действия активности распределяются по участникам (WebUI, RestApi, сервисы, SMTP); сообщения соответствуют методам REST API из SRS 3.1.3 и сервисам из SDD DV-002; фрагмент `alt` повторяет ветвление «бронь истекла / действует».
4. **Прецедент ↔ требование.** Каждый прецедент ссылается на REQ-FUNC в SRS; каждая диаграмма — на прецеденты и требования (таблица в `docs/uml.md`).
5. **Глоссарий.** Названия сущностей и состояний берутся из `docs/glossary.md`.

### Последствия

* Хорошо, потому что диаграммы обновляются в том же Pull Request, что и код и документы
* Хорошо, потому что единые имена событий и состояний упрощают проверку согласованности
* Плохо, потому что нотация Mermaid не полностью соответствует UML 2.5 (например, нет полноценных линий жизни с событиями уничтожения)
* Плохо, потому что для вариантов использования приходится поддерживать PlantUML-текст и отдельный рендер

### Подтверждение

Ревью Pull Request: каждый прецедент имеет описание и ссылку на требование; названия событий состояний совпадают с действиями активности и сообщениями последовательности; все диаграммы из `uml/src/*.mmd` отображаются на GitHub без ошибок.

## Плюсы и минусы вариантов

### Mermaid для активности, состояний и последовательности и PlantUML-текст для вариантов использования

* Хорошо, потому что нативное отображение в GitHub
* Хорошо, потому что компактный текст и читаемый diff
* Нейтрально, потому что два текстовых синтаксиса
* Плохо, потому что часть элементов UML не поддерживается

### PlantUML для всех диаграмм

* Хорошо, потому что полнее соответствует UML 2.5
* Плохо, потому что GitHub не отображает PlantUML нативно, нужен рендер и отдельные картинки

### Графический редактор (draw.io, Rational Rose)

* Хорошо, потому что удобное рисование и точная нотация
* Плохо, потому что бинарные или XML-файлы плохо сравниваются в diff, согласованность поддерживается вручную

## Дополнительная информация

Затрагивает SDD DV-013…DV-016, `docs/use-cases.md`, `docs/uml.md`, `docs/glossary.md`, `docs/supplementary-spec.md`. Растровая диаграмма вариантов использования `uml/usecase.png` создана скриптом `uml/build_usecase.py` (matplotlib) по той же структуре, что и PlantUML-текст, так как PlantUML не был доступен в среде сборки. Решение пересматривается, если потребуется генерация кода из моделей или более строгая нотация UML.
