# Первым реализуется агент для Windows, сбор событий скрыт за интерфейсом ICollector

## Контекст и постановка задачи

Агент собирает события безопасности на рабочих станциях. Механизмы сбора в Windows (журнал Security, ETW) и Linux (auditd, journald) полностью разные. Делать обе версии сразу – значит удвоить объём работы над агентом. На каких ОС работает агент первой версии и как не потерять возможность добавить другую ОС позже?

Связанные требования: REQ-PORT-001, REQ-MAINT-001, REQ-FUNC-001, REQ-FUNC-002, REQ-FUNC-005. Элемент дизайна: DV-002.

## Драйверы решения

* Рабочие станции Заказчика работают под Windows 10 22H2 и Windows 11 (REQ-PORT-001).
* Срок выпуска первой версии.
* Возможность добавить агент для Linux без переделки остальных частей (REQ-MAINT-001).

## Рассмотренные варианты

* Агент только для Windows с интерфейсом ICollector
* Агенты для Windows и Linux сразу
* Кроссплатформенный агент на osquery

## Итог решения

Выбранный вариант: «Агент только для Windows с интерфейсом ICollector», потому что он покрывает все рабочие станции Заказчика и укладывается в срок, а интерфейс ICollector сохраняет возможность добавить Linux отдельной реализацией.

### Последствия

* Хорошо, потому что основной сценарий (неудачный вход, событие 4625) берётся прямо из журнала Windows.
* Хорошо, потому что агент можно отлаживать на машине разработчика и в виртуальной машине Hyper-V.
* Плохо, потому что события Linux-серверов в первой версии не собираются.

### Подтверждение

Код агента вне каталога `agent/windows` не содержит вызовов WinAPI, что проверяется на ревью. CI собирает агент на `windows-latest`.

## Плюсы и минусы вариантов

### Агент только для Windows с интерфейсом ICollector

* Хорошо, потому что объём работы минимален.
* Хорошо, потому что новая ОС добавляется отдельным классом.
* Плохо, потому что Linux пока не поддерживается.

### Агенты для Windows и Linux сразу

* Хорошо, потому что покрываются и серверы на Linux.
* Плохо, потому что работа над агентом удваивается и срок не выдерживается.

### Кроссплатформенный агент на osquery

* Хорошо, потому что сбор событий уже реализован.
* Плохо, потому что это крупная внешняя зависимость, которую трудно проверить и объяснить.
* Плохо, потому что буферизацию и защищённую доставку всё равно пришлось бы писать самим.

## Дополнительная информация

Решение пересматривается, если у Заказчика появятся рабочие станции под Linux. Агент для Linux запланирован на версию 1.1.

На диаграмме прецедентов (DV-013) внешним актёром выступает «Контролируемый хост» с ОС Windows, а источники событий агента показаны сигналом «Событие ОС получено» на диаграмме активности AD-01 (DV-014).
