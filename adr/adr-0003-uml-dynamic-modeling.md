# ADR-0003: Построение UML-моделей динамического поведения и связи между ними

- **Статус:** принято
- **Дата:** 24.11.2026
- **Автор:** _ФИО_

## Контекст

Для проекта DoneDeal нужно описать динамическое поведение системы так, чтобы его можно было хранить в Git рядом с кодом, проверять в pull request и использовать при разработке. Модели должны быть согласованы между собой и с требованиями из SRS и SDD.

## Решение

**1. Текстовое описание диаграмм.** Диаграммы заданы текстом: use case и activity — на языке DOT (Graphviz), state и sequence — на Mermaid. Исходники лежат в `docs/uml/src/`, готовые PNG — в `docs/uml/img/`. Текстовый формат даёт читаемые различия в pull request.

**2. Порядок построения и связи моделей.**

| Шаг | Модель | Из чего строится |
|---|---|---|
| 1 | Глоссарий | Термины SRS и SDD, чтобы все модели использовали одни и те же названия |
| 2 | Use case | Функциональные требования FR-xx: каждое требование реализуется одним или несколькими прецедентами |
| 3 | Activity | Основные потоки прецедентов объединяются в один процесс: действия диаграммы — это шаги потоков событий |
| 4 | State machine | Статусы сущностей из SDD (Task, Payment) становятся состояниями; переходы — это действия из activity-диаграммы |
| 5 | Sequence | Один прецедент (UC-10) детализируется до сообщений между модулями; сообщения совпадают с REST-интерфейсами из SDD |

**3. Правила построения use case диаграммы.**

- Актёры находятся вне системы; связи между актёрами не показываются. Обобщение актёров не используется, так как поведение Заказчика и Исполнителя различается.
- Каждый прецедент инициируется актёром: стрелка идёт от актёра к прецеденту. Для внешних систем (платёжный шлюз, почтовый сервис) стрелка идёт от прецедента к актёру, потому что система обращается к ним сама.
- Время выделено как актёр, потому что от него зависит запуск напоминаний (UC-17).
- `include` применяется для обязательного повторяющегося поведения (аутентификация, резервирование, выплата, запрос отзыва), `extend` — для необязательного (вложения к задаче).
- Прецеденты не соединяются между собой связью коммуникации: диаграмма описывает доступные функции, а не порядок их выполнения. Порядок показан на activity-диаграмме.

**4. Описание прецедентов** содержит краткое описание, предусловия, основной поток, альтернативные потоки и ошибки, постусловия.

## Последствия

- (+) Диаграммы версионируются в Git, их легко обсуждать в pull request.
- (+) Прослеживаемость: FR → прецедент → действие → состояние → сообщение.
- (−) Автоматическая раскладка не позволяет точно управлять положением элементов; при изменении модели PNG нужно перерисовывать.
- (−) Нужно поддерживать согласованность нескольких файлов при изменении требований.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Графические редакторы (draw.io, Rational Rose) | Бинарные или громоздкие файлы, неудобные различия в Git |
| PlantUML | Требует Java и внешний сервис для отрисовки; Mermaid отображается в GitHub сразу |
| Только текстовое описание без диаграмм | Хуже воспринимается заказчиком и командой |
