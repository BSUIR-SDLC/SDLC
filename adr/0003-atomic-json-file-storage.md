# ADR-0003: Атомарное файловое хранилище JSON с резервной копией вместо внешней СУБД

## Контекст и постановка задачи

Серверу магазина `FlowerBoxServer.exe` необходимо постоянно хранить каталог букетов, список цветов конструктора, пользователей, активные сессии, заказы, чаты с флористом и отзывы (REQ-SRV-001, REQ-REL-001). Объём данных одного цветочного магазина невелик (десятки позиций каталога, сотни-тысячи заказов и сообщений), при этом сервер запускается на обычном рабочем ПК флориста под Windows без системного администратора.

**Проблема:** какую подсистему хранения данных выбрать для сервера магазина, чтобы гарантировать целостность данных при внезапном выключении ПК и нулевые затраты на администрирование?

## Драйверы решения

* **Надёжность (REQ-REL-001):** данные заказов и каталога не должны повреждаться при аварийном завершении процесса или отключении питания.
* **Автономность развёртывания:** отсутствие необходимости устанавливать и настраивать PostgreSQL/MySQL на ПК магазина.
* **Простота резервного копирования и отладки:** читаемый формат данных и автоматическая резервная копия.
* **Производительность:** чтение и запись состояния магазина должны занимать единицы миллисекунд.

## Рассмотренные варианты

* **Вариант 1:** Атомарное файловое хранилище JSON (`data.json.tmp` → flush → `data.json.bak` → rename в `data.json`) + каталог изображений.
* **Вариант 2:** Встроенная СУБД SQLite (`Qt6::Sql`).
* **Вариант 3:** Клиент-серверная СУБД PostgreSQL.

## Итог решения

Выбранный вариант: **«Атомарное файловое хранилище JSON с резервной копией»**, потому что для нагрузки одного магазина (все данные помещаются в оперативной памяти `ShopServer` и сериализуются за < 5 мс) атомарная перезапись через временный файл и автоматический `.bak` обеспечивает защиту от повреждения файла при сбое питания, не требует SQL-миграций и дополнительных драйверов БД, а при старте сервер автоматически восстанавливается из `.bak`, если основной файл повреждён.

### Последствия

* **Хорошо**, потому что операции чтения API (каталог, конструктор, заказы) выполняются мгновенно из памяти без дисковых задержек.
* **Хорошо**, потому что формат JSON прозрачен для инспекции, ручного бэкапа и автотестов.
* **Хорошо**, потому что схема атомарной записи (`tmp` → `bak` → `rename`) исключает частично записанный файл.
* **Плохо**, потому что при росте числа заказов сверх десятков тысяч потребуется переход на SQLite или PostgreSQL (интерфейс хранения инкапсулирован в `ShopServer`, что позволяет заменить хранилище без изменения API).
* **Плохо**, потому что не поддерживается конкурентный доступ нескольких процессов сервера к одному файлу (в архитектуре работает ровно один экземпляр `FlowerBoxServer.exe`).

### Подтверждение

Проверяется инспекцией методов сохранения/загрузки в `src/server/ShopServer.cpp` и сценариями перезапуска сервера в `tests/tst_network.cpp`.

## Плюсы и минусы вариантов

### Вариант 1: Атомарный JSON + .bak

* **Хорошо**, потому что нулевая настройка и отсутствие зависимости от `Qt6::Sql` и SQL-драйверов.
* **Хорошо**, потому что мгновенное чтение из памяти и простая структура вложенных рецептов букетов.
* **Плохо**, потому что при каждом изменении перезаписывается весь файл состояния (допустимо при размере < 1–5 МБ).

### Вариант 2: SQLite

* **Хорошо**, потому что поддерживает ACID-транзакции и индексированные выборки на больших объёмах.
* **Плохо**, потому что требует проектирования реляционной схемы, SQL-запросов, миграций и поставки плагина `qsqlite`.

### Вариант 3: PostgreSQL

* **Хорошо**, потому что подходит для крупных сетей с высокой конкурентной нагрузкой.
* **Плохо**, потому что избыточно для одного магазина и требует установки и администрирования отдельного сервера БД.

* Затронутые элементы SDD: `VIEW-01` (`AtomicFileStore`), `VIEW-03` (`InformationModel`), `VIEW-05` (`Deployment`).
