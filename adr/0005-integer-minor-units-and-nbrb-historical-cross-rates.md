# Хранение денег в целых сотых долях (`long`), количеств в тысячных (`milli`) и исторический кросс-курс через BYN по API НБРБ

## Контекст и постановка задачи

Cheq учитывает покупки в шести валютах (`BYN`, `RUB`, `EUR`, `USD`, `KZT`, `PLN`), весовые и штучные товары (например, `0,75 кг` или `2 шт.`), а также формирует месячную сводку расходов и остаток бюджета в выбранной пользователем общей валюте (`REQ-FUNC-009`, `REQ-FUNC-010`, `REQ-FUNC-011`, `REQ-INT-004`). При этом исторические сводки не должны «плавать» при изменении сегодняшнего курса, исходная сумма и валюта чека должны оставаться неизменными, а погрешность округления не должна накапливаться (контрольная точность до `0,01`, `BG-03`).

Как представить денежные суммы, количества и алгоритм мультивалютного пересчёта в `:core` и SQLite?

## Драйверы решения

* **Точность финансовых расчётов (`BG-03`, `REQ-FUNC-004`, `REQ-FUNC-010`):** полное исключение двоичных ошибок `float`/`double` и двойного округления при кросс-курсах.
* **Историческая неизменность (`REQ-INT-004`, `REQ-FUNC-010`):** пересчёт строго по официальному курсу на дату покупки, с учётом масштаба котировки (`Cur_Scale`, например `100 RUB`) и деноминации BYR → BYN от `2016-07-01`.
* **Честность при офлайне (`REQ-FUNC-011`, `REQ-AVAIL-001`):** отсутствие курса никогда не подменяется нулём или сегодняшним курсом; кэшированные курсы работают полностью офлайн.
* **Отсутствие платных валютных API (`REQ-COST-001`):** публичный REST API НБРБ (`https://api.nbrb.by/exrates/rates`) бесплатен и не требует API-ключа.

## Рассмотренные варианты

* **Вариант 1: Целые `long` (минорные сотые доли и тысячные доли количества) + рациональный кросс-курс через BYN (`BigDecimal` с однократным `HALF_UP`) + локальный кэш SQLite `exchange_rates` по API НБРБ**
* **Вариант 2: Хранение сумм в `double` / `REAL` и пересчёт по текущему курсу на момент просмотра**
* **Вариант 3: Конвертация суммы чека в базовую валюту в момент сохранения без хранения исходной валюты**

## Итог решения

Выбранный вариант: **«Целые `long` (минорные сотые доли и тысячные доли количества) + рациональный кросс-курс через BYN (`BigDecimal` с однократным `HALF_UP`) + локальный кэш SQLite `exchange_rates` по API НБРБ»**, потому что он гарантирует точную десятичную арифметику без ошибок плавающей точки, сохраняет первичные суммы в исходной валюте (`REQ-FUNC-009`), выполняет кросс-пересчёт `(amount * srcRate * dstScale) / (srcScale * dstRate)` с единственным округлением и честно маркирует неполные сводки при отсутствии курса.

### Последствия

* Хорошо, потому что в SQLite хранятся компактные `INTEGER` (`total_minor`, `unit_minor`, `line_minor`, `quantity_milli`, `limit_minor`) с `CHECK`-ограничениями и проверкой переполнения через `Math.addExact`/`Math.subtractExact`.
* Хорошо, потому что при смене общей валюты (например, с `BYN` на `EUR`) исходные чеки остаются нетронутыми, а сводка пересчитывается детерминированно по кэшу `exchange_rates`.
* Хорошо, потому что `HistoricalRate.modernScale()` автоматически учитывает деноминацию до `2016-07-01` (множитель `10 000`), а `NbrbRateClient` поддерживает резервный запрос по ISO-коду (`?parammode=2`) для исторических ежемесячных котировок.
* Хорошо, потому что в `ReceiptStore.statsConverted()` и `cardSpending()` при отсутствии хотя бы одного курса возвращается `missingRateCount > 0` (`complete() == false`), и UI не показывает ложный окончательный остаток бюджета (`REQ-FUNC-011`, `REQ-FUNC-013`).
* Плохо, потому что для пересчёта двух иностранных валют (например, `USD → EUR`) требуются оба курса к `BYN` на дату покупки (при первом просмотре без кэша выполняется обращение к API НБРБ).
* Плохо, потому что все поддерживаемые валюты ограничены 2 знаками после запятой (для валют без минорных долей вроде JPY потребуется расширение модели).

### Подтверждение

1. Инспекция `Money.java`, `HistoricalRate.java`, `NbrbRateClient.java`, `HistoricalRateRepository.java` и `ReceiptStore.statsConverted()`.
2. Модульные тесты `HistoricalRateTest`, `NbrbRateClientTest`, `BudgetProgressTest`, `ReceiptCoreTest` (`:core`) и `HistoricalRatesStoreTest`, `MixedCurrencyUiTest`, `RateRefreshLifecycleTest` (`:app`).

## Плюсы и минусы вариантов

### Целые `long` + рациональный кросс-курс НБРБ + кэш SQLite

Первичные суммы в `long` (×100), количества в `long` (×1000), курсы в `exchange_rates(currency, purchase_date, scale, official_rate)`.

* Хорошо, потому что исключены двоичные ошибки (`0.1 + 0.2 != 0.3`) и промежуточные округления при кросс-курсах.
* Хорошо, потому что кэш обеспечивает мгновенный офлайн-расчёт без сетевых задержек на UI-потоке.
* Плохо, потому что требует аккуратного форматирования и парсинга строкового ввода в `Money.java`.

### `double` / `REAL` и пересчёт по сегодняшнему курсу

Хранение чисел с плавающей точкой и запрос одного актуального курса в день.

* Хорошо, потому что проще реализация на старте.
* Плохо, потому что **нарушает `REQ-FUNC-010` и `BG-03`**: прошлые месячные отчёты меняются каждый день, а `double` порождает расхождения в `0,01` на суммах.

### Немедленная конвертация при сохранении

Пересчёт покупки в одну валюту при записи без сохранения исходной валюты.

* Хорошо, потому что упрощает SQL-запросы сводок.
* Плохо, потому что **нарушает `REQ-FUNC-008` и `REQ-FUNC-009`**: теряется исходная валюта чека и невозможно корректно сменить общую валюту отчёта или посмотреть историю цен товара в исходной валюте.
