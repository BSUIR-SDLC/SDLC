# Дополнительные спецификации RuleHook

Версия 1.0 (лабораторная работа №5). Требования, которые действуют для всей системы или для нескольких прецедентов и поэтому не описываются в потоках событий отдельных прецедентов. Классификация – FURPS+. Ссылки ведут на требования SRS 0.3 (srs/srs-rulehook.md) и решения ADR.

## 1 Функциональность (общие механизмы)

| ID | Требование | Источник |
|---|---|---|
| SUP-F-01 Аудит | Каждое изменение правила, источника, цели, пользователя и включение глобальной паузы записывается в журнал аудита: кто, когда, что, старое и новое значение | REQ-FUNC-011 |
| SUP-F-02 Аутентификация | Веб-консоль и API управления доступны только после входа (UC-01); вебхуки аутентифицируются подписью источника, а не сессией | REQ-FUNC-001, REQ-SEC-001 |
| SUP-F-03 Авторизация | Права проверяются на сервере для каждого запроса по роли (таблица ролей в glossary.md, раздел 4) | REQ-SEC-003 |
| SUP-F-04 Локализация | Интерфейс и сообщения об ошибках – на русском языке; коды ошибок API – латиницей (BAD_SIGNATURE и т. д.) | SRS 2.4 |
| SUP-F-05 Время | Все отметки времени хранятся в UTC, в консоли показываются в часовом поясе Europe/Minsk | SRS 2.4 |

## 2 Удобство использования

| ID | Требование | Источник |
|---|---|---|
| SUP-U-01 | Оператор, знакомый с форматом правил, создаёт и включает новое правило не более чем за 5 минут без помощи разработчика | BG-1, REQ-FUNC-009 |
| SUP-U-02 | Ошибка проверки правила указывает путь к полю и причину, например `$.when.all[1].op: неизвестный оператор` | REQ-FUNC-004 |
| SUP-U-03 | Для любого события журнал показывает, какие правила сработали, какие нет и почему (explain) | REQ-FUNC-011 |

## 3 Надёжность

| ID | Требование | Источник |
|---|---|---|
| SUP-R-01 | Принятое событие (ответ 202) не теряется при перезапуске сервиса: событие, совпадения и доставки фиксируются одной транзакцией | REQ-REL-003, ADR-0004 |
| SUP-R-02 | Повторная доставка одного события эмулятором не создаёт повторных действий | REQ-REL-004, BR-03 |
| SUP-R-03 | Доставка действий – at-least-once с ключом идемпотентности | REQ-REL-002, ADR-0006 |
| SUP-R-04 | Недоступность одной цели не замедляет приём вебхуков и доставку в другие цели | REQ-REL-001, ADR-0004 |
| SUP-R-05 | Цепочка правил прерывается не позднее третьего перехода | REQ-FUNC-014, ADR-0008 |

## 4 Производительность

| ID | Требование | Источник |
|---|---|---|
| SUP-P-01 | Решение о совпадении принимается не более чем за 50 мс при 200 активных правилах | REQ-PERF-001, REQ-PERF-003 |
| SUP-P-02 | При 50 событиях в секунду время от приёма события до отправки действия не превышает 2 с (95-й процентиль) | BG-3, REQ-PERF-002 |

## 5 Сопровождаемость

| ID | Требование | Источник |
|---|---|---|
| SUP-S-01 | Модули сервера обращаются друг к другу только через публичный интерфейс; пакеты rule-dsl и webhook-signature не зависят от Fastify и БД | REQ-MAINT-001, ADR-0001 |
| SUP-S-02 | Покрытие модульными тестами ядра (engine, guard, dispatcher, rule-dsl, webhook-signature) – не менее 80 % строк | REQ-MAINT-001 |
| SUP-S-03 | Каждая UML-модель хранится в uml/models как текст PlantUML и начинается комментарием «Связи»; изображения строятся скриптом tools/uml_render.py | ADR-0009 |
| SUP-S-04 | Таблица переходов автомата доставки совпадает с диаграммой state-delivery.puml, что проверяется тестом в CI | ADR-0010 |

## 6 Ограничения проектирования и интерфейсы

| ID | Требование | Источник |
|---|---|---|
| SUP-D-01 | TypeScript, Node.js 24, Fastify, PostgreSQL 16, Docker Compose на одном VPS | CON-1, CON-4, ADR-0001, ADR-0007 |
| SUP-D-02 | Правила не содержат исполняемого кода; допустимы только операторы из списка | REQ-SEC-004, ADR-0002 |
| SUP-I-01 | Вход: `POST /hooks/{sourceId}`, тело – JSON до 1 МиБ, заголовки `X-RuleHook-Signature`, `X-Hop` | REQ-INT-001 |
| SUP-I-02 | Выход: POST на цель, заголовки `Idempotency-Key`, `X-Hop`, тайм-аут 5 с | REQ-INT-002 |
| SUP-L-01 | Персональные данные в событиях не ожидаются; поля из списка маскирования не показываются в журнале | REQ-SEC-005-2, REQ-COMP-001 |

## 7 Бизнес-правила

В потоках событий прецедентов вместо повторения условий даётся ссылка на правило.

| ID | Правило | Прецеденты |
|---|---|---|
| BR-01 | Вебхук принимается только при верной подписи HMAC-SHA256 по сырому телу. Подпись проверяется до разбора JSON и обращения к правилам. После ротации секрета 24 ч принимается и старый секрет | UC-02, UC-05 |
| BR-02 | Тело вебхука – не более 1 МиБ; больший запрос отклоняется ответом 413 без проверки подписи | UC-02 |
| BR-03 | Событие уникально по паре (источник, id события). Повторная доставка получает ответ 200 и не обрабатывается повторно | UC-02 |
| BR-04 | Активные правила источника и типа события проверяются по возрастанию priority, при равенстве – по id. Срабатывают все правила, условия которых выполнены | UC-10, UC-12 |
| BR-05 | Событие, совпадения и доставки сохраняются в одной транзакции; ответ 202 отправляется только после COMMIT | UC-02, UC-10 |
| BR-06 | Если X-Hop входящего события ≥ 3, доставки создаются в статусе SKIPPED с причиной HOP_LIMIT | UC-10, UC-14 |
| BR-07 | Правило не срабатывает повторно для того же источника в течение cooldownSec; такие доставки получают статус SKIPPED с причиной COOLDOWN | UC-10 |
| BR-08 | Правило, сработавшее более 20 раз за 60 с, автоматически выключается; причина пишется в журнал, оператор получает уведомление | UC-14 |
| BR-09 | Ответы 408, 429, 5xx, тайм-аут 5 с и сетевые ошибки повторяются: всего не более 5 попыток (первая и 4 повтора) с паузой 2, 4, 8, 16 с, затем доставка становится недоставленной; остальные 4xx не повторяются (ADR-0006) | UC-09 |
| BR-10 | Ключ идемпотентности доставки равен её id и не меняется ни при автоматическом, ни при ручном повторе | UC-08, UC-09 |
| BR-11 | События и доставки хранятся 30 суток, недоставленные – до повтора, но не более 90 суток; затем удаляются | UC-13 |
| BR-12 | При глобальной паузе вебхуки принимаются и сопоставляются, новые доставки ждут в статусе PAUSED; после снятия паузы отправляются в порядке создания | UC-07 |
