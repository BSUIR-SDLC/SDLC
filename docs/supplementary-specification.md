# Дополнительные спецификации Task Manager

Версия 0.3. Подготовила Климова Авелина Алексеевна. Дата: 23.11.2026.

Документ задаёт общие условия [прецедентов](use-cases.md) и [динамических моделей](../diagrams/dynamic_modeling/README.md). Это проектные правила версии 0.3. Критерии приложения остаются Planned.

## SUP-001 Доступ и роли

Регистрация и вход доступны гостю. Все операции с личными данными требуют действующей сессии и незаблокированного аккаунта. ownerId берётся из контекста приложения, а не из редактируемой формы. Администратор наследует возможности обычного пользователя для собственных задач; административная роль не открывает чужие списки дел. Роль не выбирается при публичной регистрации.

## SUP-002 Ввод и валидация

Название задачи и подзадачи после удаления крайних пробелов содержит 1–200 символов; описание задачи — до 5000. Название категории — 1–100 символов и уникально у владельца. Приоритет — одно из четырёх значений SRS; по умолчанию обычный. Дедлайн и категория необязательны, но заданная категория принадлежит владельцу, а заданная дата однозначно преобразуется в UTC. Ошибка формы не сохраняет частичные изменения.

## SUP-003 Состояния

Сохранённая задача начинается как «Новая», затем может перейти в «В работе» или сразу в «Выполнена». Из «В работе» допускается завершение. Из любого из этих состояний возможно подтверждённое удаление. Восстановление и повторное открытие выполненной задачи в выбранный жизненный цикл не входят. Просроченность = незавершённая задача с deadline < now; равенство момента дедлайну ещё не означает просроченность.

## SUP-004 Подзадачи и категории

Прогресс = floor(completed / total × 100%); при total=0 выводится «Нет подзадач». Готовность всех подзадач не завершает родительскую задачу автоматически. Удаление категории снимает её назначение, сохраняя задачи. Удаление задачи исключает её подзадачи из дальнейших операций в одной транзакции.

## SUP-005 Повторение

Правило доступно задаче с дедлайном. Следующий срок рассчитывается календарно в zone_id владельца: следующий день, следующий выбранный день недели либо заданное число месяца; в коротком месяце используется последний день. Если даты пропущены, выбирается первый допустимый срок после now без массового создания пропущенных экземпляров. Неоднозначный местный момент при переходе часов разрешается более ранним UTC-смещением, несуществующий сдвигается вперёд на величину разрыва; это правило должно проверяться тестами.

После первого завершения создаётся ровно один новый экземпляр со статусом «Новая», новым ID, рассчитанным сроком, теми же владельцем, описанием, приоритетом, категорией и правилом. Подзадачи копируются как невыполненные. Завершение исходной задачи и создание следующей выполняются атомарно; unique(source_task_id) защищает от повторного создания. Исходная запись остаётся выполненной. Удаление не порождает следующий экземпляр.

## SUP-006 Поиск и CSV

Поиск по названию не зависит от регистра. Фильтры статуса, приоритета, категории и просроченности применяются совместно только к данным владельца. Пустой результат — нормальное состояние. При равных значениях сортировки ID обеспечивает стабильный порядок. CSV сохраняет ранее определённый контракт версии 0.2; четыре UML-модели показывают выбранные сценарии, а не отменяют экспорт.

## SUP-007 Сохранение и конфликты

TaskController передаёт действие TaskService, который проверяет сессию, владельца и ввод. TaskRepository сохраняет данные через Qt SQL в SQLite. UI подтверждает результат только после commit. Версия записи проверяется при обновлении/завершении; при конфликте отображается предложение перечитать данные вместо незаметной перезаписи. Обозначение 409 в исторической модели — логический Conflict, а не обязательный HTTP-ответ desktop-приложения.

## SUP-008 Аккаунты и блокировка

Уникальность email проверяется при регистрации. Пароль хранится только как соль и результат адаптивного хеширования; секреты не журналируются. Роль администратора назначается вне публичной регистрации. Администратор просматривает идентификатор, email, роль и статус аккаунта, но не пароль/хеш и не чужие задачи. Создание администратора и смена его роли публично не предоставляются. Блокировка подтверждается, отзывает сессию и запрещает новые защищённые операции. Самоблокировка и блокировка последнего активного администратора запрещены.

## SUP-009 Напоминания

После наступления дедлайна незавершённой задачи создаётся задание отправки только для её владельца. Уникальный ключ (taskId, deadlineUtc) исключает повторную постановку для того же срока. Изменение дедлайна отменяет неотправленное старое задание. Завершение, удаление или блокировка владельца также отменяют неотправленное напоминание. Текст содержит название и срок задачи, без паролей и описаний подзадач.

Отправка выполняется через настраиваемый SMTP-адаптер с защищённым соединением; учётные данные находятся вне Git. Подтверждение SMTP означает принятие сообщения сервером, а не доказанную доставку пользователю. Статусы задания: pending, sending, accepted, failed, unknown. При неопределённом результате автоматический повтор не обещает exactly-once: SMTP может принять письмо до потери ответа. unknown требует сверки/явного повтора. Локальный запуск проверяет просроченные задания при старте и во время работы приложения; доставка при выключенном приложении не гарантируется. Отсутствие SMTP не блокирует сохранение задач.

## SUP-010 Диагностика

Журнал содержит время UTC, код, компонент и идентификатор корреляции. Доступ к диагностике требует роли администратора. Пароли, хеши, секреты SMTP, содержимое сессий, названия и описания чужих задач скрываются. Неудачная административная операция также фиксируется без раскрытия секретов.

## SUP-011 Границы архитектуры и графики

Стек сохраняется: C++20, Qt 6 Widgets, Qt SQL и SQLite. В копии Visio для репозитория подпись PostgreSQL приведена к SQLite без смены расположения участников. Последовательность показывает успешный createTask; ошибки описаны в UC-002/009. На графике сохранены концевые крестики пользователя: в строгом UML они означают уничтожение, но постоянные компоненты и человек не уничтожаются при создании задачи. Семантический PlantUML завершает активации без destroy; оформление следует отдельно согласовать при ревью.

## SUP-012 Проверки качества

Сохраняются критерии версии 0.2: p95 операций ≤500 мс, запуск UI ≤3 с на установленном стенде. Проверяются восстановление данных, миграции, транзакции и разграничение доступа. Просмотр PNG, проверка ссылок и синтаксиса UML не подтверждают выполнение этих критериев; статус испытаний — Planned. Новые административные функции и почта требуют собственной оценки и не включаются в бюджет P2 автоматически.
