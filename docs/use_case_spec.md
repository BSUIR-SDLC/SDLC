# Спецификация модели вариантов использования (Use-Case Specification)
## Проект: IoT Device Emulator (Вариант 8)

### 1. Описание действующих лиц (Актёров)
* **Оператор / QA-инженер** — специалист, запускающий и настраивающий эмулятор через CLI с необходимыми стартовыми параметрами и контролирующий его работу по логам.
* **Движок правил (Rule Engine)** — внешняя серверная система, которая отправляет управляющие HTTP-директивы на эндпоинт `/command` для изменения поведения эмулятора.
* **Таймер планировщика** — системное действующее лицо (время), периодически инициирующее цикл формирования и отправки очередного пакета телеметрии каждые $N$ секунд.

---

### 2. Детальное описание вариантов использования (Прецедентов)

#### UC-1: Конфигурирование и запуск эмулятора через CLI
* **Краткое описание:** Позволяет Оператору запустить сервис эмулятора с передачей параметров хоста, порта, идентификатора устройства, начального интервала $N$ и токена безопасности.
* **Предусловия:** Установлен интерпретатор Python 3.10+ и зависимости проекта; сетевой порт свободен.
* **Основной поток событий:**
  1. Оператор вводит команду запуска скрипта с флагами `--device-id`, `--port`, `--interval`, `--token`.
  2. Система валидирует аргументы командной строки.
  3. Система инициализирует асинхронный цикл событий (`event loop`), запускает фоновую задачу таймера и HTTP-сервер Uvicorn.
  4. Прецедент завершается переходом эмулятора в рабочий режим `NORMAL`.
* **Альтернативный поток А1:** Оператор не указывает необязательные флаги — система подставляет значения по умолчанию (`interval=5`, `port=8000`).
* **Поток ошибок Е1:** Указан некорректный тип аргумента или занятый порт — система выводит сообщение об ошибке в консоль и завершает работу с кодом возврата `1`.
* **Постусловия:** Эмулятор активен, генерирует телеметрию и ожидает HTTP-запросы.

#### UC-2: Периодическая генерация JSON-телеметрии
* **Краткое описание:** Обеспечивает регулярное формирование и отправку данных о состоянии виртуального датчика по срабатыванию таймера.
* **Предусловия:** Эмулятор успешно запущен (`UC-1`).
* **Основной поток событий:**
  1. Таймер планировщика отсчитывает интервал $N$ секунд.
  2. Эмулятор считывает актуальные параметры состояния (`device_id`, `mode`, `temp_offset`).
  3. Вычисляются значения `temperature` (float) и `motion` (boolean), формируется JSON-пакет с текущим `timestamp`.
  4. Пакет отправляется целевому получателю и фиксируется в журнале событий (`UC-7`).
* **Альтернативный поток А1:** Если установлен режим `ALERT`, к базовой температуре прибавляется заданное аварийное смещение (`target_temp_offset`).
* **Постусловия:** Очередной пакет телеметрии доставлен и залогирован; таймер запускает новый отсчёт на $N$ секунд.

#### UC-3: Приём и обработка управляющей команды `/command`
* **Краткое описание:** Позволяет внешнему Движку правил динамически менять параметры работы эмулятора без его перезапуска.
* **Предусловия:** HTTP-сервер эмулятора запущен и принимает подключения; у Движка правил есть валидный `Bearer Token`.
* **Основной поток событий:**
  1. Движок правил отправляет HTTP POST-запрос на `/command` с JSON-телом и заголовком `Authorization`.
  2. Система вызывает включённый прецедент проверки токена (`UC-4`).
  3. Система захватывает асинхронную блокировку (`asyncio.Lock`) для предотвращения состояния гонки.
  4. В зависимости от переданных полей выполняется расширение `UC-5` (смена интервала $N$) и/или `UC-6` (мутация состояния сенсора).
  5. Блокировка освобождается, событие фиксируется в логе (`UC-7`), клиенту возвращается ответ `200 OK`.
* **Альтернативный поток А1 (Ошибка авторизации):** Токен отсутствует или не совпадает с эталонным — система логирует попытку несанкционированного доступа и возвращает `401 Unauthorized` без изменения состояния.
* **Поток ошибок Е1:** Тело запроса содержит невалидный JSON или недопустимые значения (например, `interval_sec <= 0`) — возвращается ошибка валидации `422 Unprocessable Entity`.
* **Постусловия:** Новые параметры эмулятора атомарно сохранены и применяются со следующего цикла генерации.
