# Описание актёров и потоков событий (Flow of Events) — IoTPanel

## 1. Актёры системы

| Актёр | Тип | Описание роли в системе |
|---|---|---|
| **Оператор мониторинга** | Первичный | Отслеживает показания датчиков на живых графиках телеметрии в реальном времени, реагирует на баннеры тревоги и вручную переключает состояние устройств. |
| **Инженер автоматизации** | Первичный | Создаёт, тестирует (Dry-Run) и редактирует правила автоматизации в 4-шаговом конструкторе, а также анализирует журнал срабатываний. |
| **Device Emulator** | Вторичный | Эмулятор IoT-устройств, периодически отправляющий JSON-пакеты с телеметрией и исполняющий входящие HTTP-команды `POST /command`. |
| **Telegram / Webhook сервис** | Вторичный | Внешний шлюз доставки экстренных оповещений дежурному персоналу при срабатывании критических правил автоматизации. |

## 2. Потоки событий прецедентов

### UC-02: Переключение состояния устройства (`/command`)
- **Краткое описание:** позволяет Оператору мониторинга дистанционно включить или выключить исполнительный механизм выбранного IoT-устройства с гарантированной индикацией результата.
- **Предусловия:** Оператор авторизован в системе (выполнен включённый прецедент `UC-03`), целевое устройство находится в статусе `ONLINE`.
- **Основной поток событий:**
  1. Оператор нажимает тумблер переключения состояния на карточке устройства.
  2. Клиент блокирует повторное нажатие тумблера и отправляет запрос `POST /command` с идентификатором `device_id` и целевым состоянием.
  3. Сервер Rule Engine проверяет токен доступа и пересылает команду в Device Emulator.
  4. Эмулятор применяет состояние и возвращает код `200 OK`.
  5. Сервер записывает событие в журнал `command_history` и возвращает подтверждение клиенту.
  6. Интерфейс переводит тумблер в новое положение и отображает зелёный индикатор «Выполнено».
- **Альтернативный поток А1 (Устройство OFFLINE):** при отсутствии heartbeat-пакетов более 5 с тумблер блокируется (`disabled`), отображается статус «Недоступно».
- **Поток ошибок E1 (Таймаут 504):** при отсутствии ответа от эмулятора в течение 2 с сервер возвращает `504 Gateway Timeout`, клиент откатывает тумблер в исходное положение и выводит предупреждение.
- **Постусловия:** состояние устройства обновлено, в БД зафиксирована запись аудита.

### UC-04: Создание правила автоматизации (4 шага -> JSON)
- **Краткое описание:** позволяет Инженеру автоматизации сформировать правило автоматизации через визуальный конструктор без ручного редактирования JSON-файла.
- **Предусловия:** Инженер открыл вкладку «Конструктор правил», в системе зарегистрировано хотя бы одно устройство.
- **Основной поток событий:**
  1. Инженер последовательно заполняет 4 шага: выбирает устройство, метрику (`temperature`/`motion`), условие сравнения и целевое действие.
  2. Клиент валидирует поля по JSON Schema и формирует предпросмотр JSON-правила.
  3. Инженер нажимает «Сохранить правило» (`POST /api/rules`).
  4. Сервер сохраняет правило в таблицу `automation_rules` и активирует его в движке правил.
- **Альтернативный поток А1 (Расширение UC-05 Dry-Run):** до сохранения Инженер нажимает «Тестовый прогон»; система отправляет тестовое сообщение в Telegram/Webhook без переключения реального устройства.
- **Поток ошибок E1 (Некорректные поля):** кнопка сохранения остаётся неактивной, проблемное поле подсвечивается подсказкой.
- **Постусловия:** новое JSON-правило сохранено в PostgreSQL и отображается в таблице активных правил.
