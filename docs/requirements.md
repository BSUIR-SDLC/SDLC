# Системные требования FocusFlow

**Версия:** 1.0  
**Статус:** учебная версия для ЛР4  
**Основа:** SRS проекта FocusFlow из лабораторной работы № 3.

## 1. Назначение и область применения

FocusFlow — веб-приложение для повышения личной эффективности и продуктивности. Оно помогает пользователю организовывать цели, привычки, календарные события и заметки, а также работать с командами и общими задачами в пределах назначенных прав.

## 2. Шкала приоритетов

- **10 — Critical:** обязательная функция базового выпуска.
- **20 — High:** важная функция, необходимая большинству пользователей.
- **30 — Medium:** полезная функция, допускающая реализацию после ядра.
- **40 — Low:** второстепенная функция.
- **50 — Optional:** дополнительная функция, может быть перенесена в последующий выпуск.

## 3. Функциональные системные требования

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---:|---|
| SYS-FR-001 | Система должна позволять пользователю зарегистрироваться с уникальным адресом электронной почты. | 10 | Повторная регистрация с тем же email отклоняется с понятной ошибкой. |
| SYS-FR-002 | Система должна предоставлять вход и выход из учётной записи. | 10 | При корректных данных создаётся сессия; неверные данные не дают доступ. |
| SYS-FR-003 | Система должна ограничивать доступ к личным данным владельцем этих данных. | 10 | Пользователь не может прочитать или изменить чужую цель, привычку или заметку. |
| SYS-FR-004 | Система должна позволять создавать, просматривать, изменять и удалять личные цели. | 10 | CRUD-операции сохраняются и отражаются после повторного чтения. |
| SYS-FR-005 | Система должна позволять задавать цели и отслеживать их статус. | 20 | Статус цели сохраняется и отображается в списке целей. |
| SYS-FR-006 | Система должна позволять создавать и редактировать привычки. | 10 | Пользователь может добавить привычку, изменить её параметры и удалить её. |
| SYS-FR-007 | Система должна регистрировать выполнение привычки по датам. | 20 | Отметка выполнения сохраняется и не дублируется для одной привычки и даты. |
| SYS-FR-008 | Система должна предоставлять календарное представление событий пользователя. | 20 | События отображаются на соответствующих датах. |
| SYS-FR-009 | Система должна позволять создавать, изменять и удалять календарные события. | 20 | Изменения события сохраняются и видны при повторном запросе. |
| SYS-FR-010 | Система должна позволять создавать и редактировать личные заметки. | 20 | Заметка сохраняется и доступна только владельцу. |
| SYS-FR-011 | Система должна позволять создавать команды и управлять их составом в пределах прав участника. | 30 | Операции управления составом доступны только уполномоченным участникам. |
| SYS-FR-012 | Система должна позволять приглашать пользователя в команду. | 30 | Приглашение имеет корректный статус и не создаёт дублирующего членства. |
| SYS-FR-013 | Система должна проверять членство и роль пользователя перед командными операциями. | 10 | Запрос от неучастника или пользователя без нужной роли отклоняется. |
| SYS-FR-014 | Система должна предоставлять фильтрацию и сортировку основных списков. | 40 | Результат соответствует выбранным фильтрам и правилам сортировки. |
| SYS-FR-015 | Система должна экспортировать согласованный набор пользовательских данных в CSV. | 30 | CSV содержит заголовки и корректно экранированные значения; доступен только владельцу данных. |

## 4. Нефункциональные системные требования

| ID | Требование | Проверка/критерий |
|---|---|---|
| SYS-NFR-001 | Передача данных между клиентом и сервером должна выполняться по защищённому каналу в production-среде. | Проверка конфигурации HTTPS/TLS. |
| SYS-NFR-002 | Пароли не должны храниться в открытом виде. | Проверка схемы хранения и тест аутентификации. |
| SYS-NFR-003 | Сервер должен проверять входные данные на стороне backend. | Негативные тесты для некорректных значений. |
| SYS-NFR-004 | Проверки прав доступа должны выполняться на сервере для каждого защищённого запроса. | Тесты доступа между разными пользователями и ролями. |
| SYS-NFR-005 | Операции изменения связанных данных должны быть транзакционными там, где частичное выполнение нарушает целостность. | Тест отката при ошибке операции. |
| SYS-NFR-006 | Для основных операций с личными списками целевой ответ сервера должен составлять не более 2 секунд при типовой учебной нагрузке. | Нагрузочный тест с зафиксированными условиями. |
| SYS-NFR-007 | Система должна возвращать единообразные ответы об ошибках без раскрытия секретов и внутренних трассировок. | Проверка API-ответов на негативных сценариях. |
| SYS-NFR-008 | Код серверных модулей должен быть разделён по ответственности и пригоден для модульного тестирования. | Проверка структуры и наличия тестов сервисного слоя. |
| SYS-NFR-009 | Схема базы данных должна поддерживать ограничения целостности для ключевых сущностей и связей. | Проверка ограничений и тесты некорректных связей. |
| SYS-NFR-010 | Документация API и архитектурных решений должна обновляться вместе с изменениями поведения системы. | Проверка документации в pull request. |

## 5. Допущения и ограничения

- FocusFlow рассматривается как веб-приложение с клиентской частью и серверным API.
- Подробные бизнес-правила должны соответствовать согласованному SRS из ЛР3.
- CSV-экспорт включён в итоговую учебную версию P2 как изменение CHG-002.
- Точные названия технологий и библиотек необходимо сверить с SRS/репозиторием ЛР3.
