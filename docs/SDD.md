# Software Design Description (SDD) — FocusFlow

**Версия:** 1.0  
**Статус:** проектное описание для лабораторной работы № 4  
**Связанные документы:** SRS ЛР3, `requirements.md`, ADR-001…ADR-005.

## 1. Введение

### 1.1 Цель
Документ описывает системную архитектуру FocusFlow, основные программные компоненты, их взаимодействие, данные, интерфейсы и архитектурные ограничения.

### 1.2 Область применения
FocusFlow помогает пользователю управлять целями, привычками, календарём, заметками и командной работой. В итоговый план P2 включён экспорт выбранных данных в CSV.

### 1.3 Термины
- **API** — программный интерфейс взаимодействия клиентской и серверной частей.
- **CRUD** — создание, чтение, изменение и удаление сущности.
- **ADR** — запись о принятом архитектурном решении.
- **RBAC** — управление доступом на основе ролей.
- **P0/P1/P2** — последовательные версии оценки и плана проекта.

## 2. Обзор системы

Система состоит из клиентского веб-интерфейса, серверного API, прикладного слоя с бизнес-правилами и реляционного хранилища. Сервер является доверенной границей: аутентификация, валидация, проверка владения данными и командных ролей выполняются на backend.

### 2.1 Основные сценарии
1. Пользователь регистрируется и входит в систему.
2. Создаёт и обновляет личные цели.
3. Добавляет привычки и фиксирует выполнение по датам.
4. Создаёт календарные события и заметки.
5. Создаёт команду или выполняет разрешённые действия в существующей команде.
6. Экспортирует доступные ему данные в CSV.

## 3. Архитектура

### 3.1 Архитектурный стиль
Для учебной версии выбран модульный монолит: один серверный deployable-компонент, внутри которого логика разделена на модули по предметным областям. Это уменьшает сложность развёртывания и сохраняет возможность дальнейшего выделения модулей при росте нагрузки.

### 3.2 Логические компоненты

| Компонент | Ответственность |
|---|---|
| Web Client | Формы, навигация, отображение целей, привычек, календаря, заметок и команд. |
| API / Controllers | Приём HTTP-запросов, проверка формата, преобразование запросов и ответов. |
| Authentication | Регистрация, вход, завершение сессии и идентификация пользователя. |
| Authorization | Проверка владельца данных, членства в команде и роли участника. |
| Goals Service | Правила работы с целями и их статусами. |
| Habits Service | Управление привычками и отметками выполнения. |
| Calendar Service | Управление календарными событиями. |
| Notes Service | Управление личными заметками. |
| Teams Service | Команды, участники, приглашения и проверки ролей. |
| Export Service | Формирование CSV из данных, к которым пользователь имеет доступ. |
| Persistence Layer | Репозитории, транзакции и взаимодействие с реляционной БД. |

### 3.3 Общий поток запроса
1. Клиент отправляет HTTPS-запрос к API.
2. API проверяет аутентификацию и валидирует входные данные.
3. Слой авторизации проверяет право пользователя на действие.
4. Прикладной сервис выполняет бизнес-операцию.
5. Слой хранения читает или изменяет данные; связанные изменения выполняются транзакционно.
6. API возвращает результат либо стандартизированную ошибку.

## 4. Данные

Основные сущности:
- `User` — пользователь и данные учётной записи.
- `Goal` — личная цель, владелец, описание, статус и даты.
- `Habit` — привычка и параметры повторения.
- `HabitCompletion` — отметка выполнения привычки за дату.
- `CalendarEvent` — событие календаря, владелец, время и описание.
- `Note` — личная заметка.
- `Team` — команда.
- `TeamMembership` — связь пользователя с командой и его роль.
- `TeamInvitation` — приглашение и его статус.

### 4.1 Ограничения целостности
- Идентификаторы сущностей уникальны.
- Каждая личная сущность связана с владельцем.
- Для отметок выполнения задаётся ограничение уникальности по привычке и дате, если по правилам продукта допускается только одна отметка в день.
- Членство пользователя в одной команде не должно дублироваться.
- Внешние ключи и транзакции защищают согласованность связанных данных.

## 5. Интерфейсы

### 5.1 API
Взаимодействие выполняется через HTTP REST API. Конкретные пути должны быть согласованы с реализацией и SRS ЛР3. Рекомендуемые группы маршрутов:
- `/api/auth` — регистрация и аутентификация;
- `/api/goals` — цели;
- `/api/habits` и `/api/habits/{id}/completions` — привычки и выполнение;
- `/api/calendar/events` — календарные события;
- `/api/notes` — заметки;
- `/api/teams` — команды и членство;
- `/api/export/csv` — экспорт данных.

### 5.2 Формат ошибок
API возвращает код HTTP и структурированное сообщение об ошибке. В production-ответах нельзя раскрывать пароли, токены, SQL-запросы или внутренние stack trace.

## 6. Безопасность
- Все защищённые операции требуют действительной аутентификации.
- Проверка прав выполняется на сервере, а не только в пользовательском интерфейсе.
- Пользователь может читать и изменять только свои личные данные.
- Командные действия разрешены в соответствии с членством и ролью.
- Пароли хранятся в виде стойкого хеша с солью.
- Входные данные валидируются до выполнения бизнес-операций.
- Секреты и конфигурация окружения не включаются в репозиторий.

## 7. Нефункциональные аспекты
- Целевое время ответа основных операций — до 2 секунд при типовой учебной нагрузке; измерение должно фиксировать окружение и нагрузку.
- Модули должны иметь ясные границы и тестироваться независимо на уровне сервисов.
- Изменения связанных сущностей должны сохранять целостность.
- Логи не должны содержать пароли, токены и лишние персональные данные.

## 8. Тестирование
- Unit-тесты бизнес-правил сервисов.
- Интеграционные тесты API и слоя хранения.
- Негативные тесты аутентификации и авторизации.
- Проверки целостности данных и транзакционного отката.
- Проверки формирования CSV и недоступности чужих данных.
- Проверки критериев приёмки из `requirements.md`.

## 9. Развёртывание и эксплуатация
Окружения разработки, тестирования и production должны использовать отдельную конфигурацию. Пароли и ключи передаются через переменные окружения или менеджер секретов. Миграции схемы БД должны версионироваться.

## 10. Открытые вопросы
1. Сверить конкретный технологический стек с SRS и исходным репозиторием.
2. Уточнить точные поля CSV и формат дат.
3. Уточнить правила удаления пользователей и связанных сущностей.
4. Уточнить ограничения календарных событий и повторяемости привычек.
