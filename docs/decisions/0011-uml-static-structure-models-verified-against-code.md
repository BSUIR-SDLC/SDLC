# Статическая структура — диаграммы классов, компонентов и развёртывания UML в PlantUML, проектные классы сверяются с кодом

## Контекст и постановка задачи

В ЛР 3–4 структура QRGate описана на SysML v2 (композиция 002, данные 004, развёртывание 009), в ЛР 5 поведение —
на UML (ADR-0009). С итерации I2 начинается реализация модулей сервера (F04, F08), к работе подключается
junior-разработчик. Нужны диаграммы классов, компонентов и развёртывания, которые: 1) служат спецификацией для
реализации; 2) остаются верными по мере изменения кода; 3) связаны с требованиями, решениями и диаграммами
поведения. На каком уровне детализации строить эти диаграммы и как не допустить их расхождения с кодом?

## Драйверы решения

* SUP-S-03: модель и код не должны расходиться; расхождение должно обнаруживаться автоматически.
* REQ-MAINT-001: границы модулей и зависимости только через `index.ts` (ADR-0001) должны быть видны.
* Junior-разработчик реализует F10, F13, F14 по диаграммам — ему нужны классы с операциями и кратностями.
* Единый инструмент и формат с моделями поведения (ADR-0009); только бесплатные средства (CON-4).

## Рассмотренные варианты

* Диаграммы в PlantUML на двух уровнях (анализ и проектирование) + тест сверки проектных классов с кодом
* Генерация диаграмм классов из кода (tplant, TypeDoc + плагин UML)
* Одна диаграмма классов уровня анализа без сверки
* Расширить SysML-модели ЛР 4 (bdd/ibd) вместо UML

## Итог решения

Выбранный вариант: «PlantUML на двух уровнях + тест сверки», потому что диаграмма остаётся моделью (её можно
нарисовать раньше кода и обсудить в pull request), а тест гарантирует, что код ей соответствует.
Генерация из кода отвергнута: она показывает то, что уже написано, и не может быть спецификацией для junior.

### Механизм построения

1. Модели — `uml/models/<вид>-<предмет>.puml`; к видам ADR-0009 добавлены `class`, `component`, `deployment`.
   Рендер — тот же `python tools/uml_render.py` (фильтр по имени: `python tools/uml_render.py class`).
2. **Диаграмма классов уровня анализа** `class-domain.puml` (SDD 019) строится из глоссария и логической модели
   данных SDD 004: существительные глоссария → классы, столбцы → атрибуты с типами и значениями по умолчанию,
   связи r1–r12 → ассоциации с кратностями. Композиция (`*--`) — для частей, не существующих без целого
   (зоны и точки объекта), агрегация (`o--`) — для разделяемых частей (фото владельца), обобщение — для ролей
   пользователей и видов пропусков (BR-03), ассоциативный класс — для присутствия «пропуск × объект».
3. **Диаграммы классов уровня проектирования** `class-validation.puml`, `class-passes.puml` (SDD 020)
   строятся из диаграмм последовательности ЛР 5: каждая линия жизни → класс, каждое синхронное сообщение →
   операция получателя; зависимости от инфраструктуры выделяются в интерфейсы-порты (ADR-0012). Пакеты
   диаграммы называются путями каталогов (`package "apps/api/src/modules/validation"`).
4. **Диаграмма компонентов** `component-qrgate.puml` (SDD 021) строится из композиции 002: модуль сервера →
   компонент; публичный `index.ts` модуля → предоставляемый интерфейс (lollipop); порт сервиса → требуемый
   интерфейс (socket); соединение «шар — гнездо» показывает, какой компонент реализует порт. Порты подсистемы
   API Server с делегирующими соединителями — входы `/api/v1`, `/ws` и выход `sql` (SDD 005).
5. **Диаграмма развёртывания** `deployment-qrgate.puml` (SDD 022) строится из SysML-модели 009: устройства и
   среды выполнения (`<<device>>`, `<<executionEnvironment>>`, `<<container>>`) → узлы, результаты сборки →
   артефакты, сетевые соединения → пути связи с протоколом и портом, `<<manifest>>` — какой артефакт реализует
   компонент диаграммы 021.

### Механизм связей

* **Классы ↔ код (автоматически).** Тест `apps/api/test/classDiagram.test.ts` разбирает проектные диаграммы:
  для каждого класса, интерфейса и перечисления пакета-каталога ищет `export class|interface|type` в коде
  этого каталога, для каждой операции — её объявление, для `<<utility>>` — экспортируемую функцию; обратно —
  каждый `export class` каталога должен быть на диаграмме. Новый класс без диаграммы или удалённая операция
  роняют CI.
* **Классы ↔ поведение.** Операции `ValidationService`, `ValidationTx` — сообщения
  `sequence-validate-pass.puml`; операции `PassService` — переходы `state-pass-lifecycle.puml`; события
  кнопок `ResultCard` — события `ScannerEvent` диаграммы `state-scanner.puml` (сверка ADR-0010).
* **Классы ↔ требования.** Порядок `CheckChain.standard()` — BR-01; ограничения `PassService` — BR-02, BR-03,
  BR-05; перечисление `Reason` — контракт REQ-INT-005.
* **Компоненты ↔ код.** Компонент = каталог `apps/*`, `packages/*` или `apps/api/src/modules/*`;
  предоставляемый интерфейс = экспорт `index.ts`; требуемый интерфейс = параметр фабрики/конструктора.
* **Развёртывание ↔ компоненты и ADR.** Артефакт → компонент через `<<manifest>>`; узлы и порты совпадают
  с ADR-0007 и SDD 009, ресурсы узлов — с SDD 012.
* Каждый `.puml` начинается с комментария «Связи» (ADR-0009); SDD 019–022 и приложение В замыкают трассировку.

### Последствия

* Хорошо, потому что проектные диаграммы классов не устаревают молча — расхождение видно в CI.
* Хорошо, потому что два уровня разделяют «что есть в предметной области» и «как это устроено в коде».
* Плохо, потому что на проектной диаграмме нужно перечислять все экспортируемые классы каталога.
* Нейтрально, потому что атрибуты и кратности тестом не сверяются (только имена и операции).

### Подтверждение

`npm test`: 3 теста `classDiagram.test.ts` (45 классов двух проектных диаграмм); все пять диаграмм
строятся `python tools/uml_render.py` без ошибок; ревью pull request ветки `lab6`.

## Плюсы и минусы вариантов

### PlantUML на двух уровнях + тест сверки

* Хорошо, потому что модель первична и проверяема.
* Плохо, потому что парсер теста понимает только принятый в проекте формат записи.

### Генерация из кода

* Хорошо, потому что всегда совпадает с кодом.
* Плохо, потому что не может предшествовать коду и перегружена деталями реализации.

### Одна диаграмма анализа без сверки

* Плохо, потому что не годится как спецификация модулей и расходится с кодом незаметно.

### SysML bdd/ibd

* Хорошо, потому что одна нотация со структурой ЛР 4.
* Плохо, потому что в собственном рендере нет операций, интерфейсов «шар — гнездо» и артефактов.

## Дополнительная информация

Связанные решения: ADR-0001 (модули), ADR-0007 (развёртывание), ADR-0009 (PlantUML), ADR-0010 (сверка автомата),
ADR-0012 (порты и адаптеры). SDD 0.5, представления 019–022.
