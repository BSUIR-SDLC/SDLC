# Автомат сканера — чистая таблица переходов, сверяемая с диаграммой состояний

## Контекст и постановка задачи

Поведение сканера задано диаграммой состояний [`uml/models/state-scanner.puml`](../../uml/models/state-scanner.puml)
(SDD 007, 016). Самое опасное расхождение модели и кода — появление перехода в «Проход разрешён» не из
«Проверки» (нарушение fail-closed, ADR-0006). Как реализовать автомат, чтобы код гарантированно
соответствовал диаграмме?

## Драйверы решения

* REQ-REL-001, BG-2: из «Нет связи» нельзя попасть в «Проход разрешён».
* REQ-MAINT-001: модульные тесты без браузера и камеры.
* SUP-S-03: модель и код не должны расходиться.

## Рассмотренные варианты

* Чистая таблица переходов + редьюсер React + тест сверки с `.puml`
* Библиотека XState с визуализатором
* Флаги и `if` в компонентах React

## Итог решения

Выбранный вариант: «Чистая таблица переходов», потому что она без зависимостей, тестируется в Node и
позволяет тесту прочитать диаграмму и сравнить множества переходов. Составное состояние «Сеанс»
реализовано отдельной таблицей `SESSION_TRANSITIONS`, действующей из любого подсостояния.
Событие, отсутствующее на диаграмме, игнорируется (состояние не меняется).

### Механизм связи модели и кода

1. Переходы на диаграмме записываются строго как `источник --> цель : СОБЫТИЕ [guard] / действие`;
   имена состояний — идентификаторы `ScannerState`, имена событий — `ScannerEvent`.
2. Тест разбирает `.puml`, раскрывает составное состояние `session` в его подсостояния и вход в него —
   в начальное подсостояние, затем сравнивает множество переходов с таблицей `TRANSITIONS` в коде.
3. Действия `entry/exit/do` и guard реализуются функциями `isCameraActive`, `timerFor`, `isValidManualCode`,
   `createDuplicateFilter` и тоже покрыты тестами.

### Последствия

* Хорошо, потому что изменение диаграммы без изменения кода (и наоборот) роняет CI.
* Хорошо, потому что fail-closed проверяется тестом, а не ревью.
* Плохо, потому что запись переходов на диаграмме ограничена форматом, понятным тесту.

### Подтверждение

`apps/scanner/test/scannerMachine.test.ts`: 9 тестов, покрытие `scannerMachine.ts` 100 % строк.

## Плюсы и минусы вариантов

### Таблица переходов

* Хорошо, потому что 0 зависимостей и прямая сверка с моделью.
* Плохо, потому что нет иерархических состояний «из коробки» — решено отдельной таблицей.

### XState

* Хорошо, потому что иерархия, история, визуализатор.
* Плохо, потому что ~40 КБ в бандле сканера и собственная нотация, которую пришлось бы сверять с UML.

### Флаги в компонентах

* Плохо, потому что недопустимые сочетания флагов возможны и не проверяются (отсекающий критерий).

## Дополнительная информация

Связано с ADR-0006 (fail-closed) и ADR-0009 (модели PlantUML).
