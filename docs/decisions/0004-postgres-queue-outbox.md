# ADR-0004: Очередь доставки в PostgreSQL (FOR UPDATE SKIP LOCKED), transactional outbox

- Статус: accepted
- Дата: 12.11.2026
- Принимающий решение: М. Н. Дешко (архитектор)
- Связанные требования: REQ-REL-001, REQ-REL-003, REQ-PERF-004

## Контекст и постановка проблемы

Требуется выбрать решение: очередь доставки в PostgreSQL (FOR UPDATE SKIP LOCKED), transactional outbox.

## Драйверы решения

- REQ-REL-001 и REQ-REL-003: события и задачи не теряются при сбоях и перезапуске
- REQ-PERF-004: 50 событий в секунду
- CON-4: один VPS, минимум компонентов

## Рассмотренные варианты

- Таблица очереди в PostgreSQL
- Redis и BullMQ
- RabbitMQ
- Синхронный POST в обработчике вебхука

## Решение

Выбран вариант: **Таблица очереди в PostgreSQL**. Запись события, совпадений и задач – одна транзакция; нагрузка 50 событий в секунду для PostgreSQL невелика.

## Последствия

- Хорошо: нет потерь между сохранением и постановкой
- Хорошо: очередь переживает перезапуск
- Плохо: при росте нагрузки на порядок потребуется брокер

## Подтверждение

тест перезапуска воркера; нагрузочный тест F18 (50 событий/с, 10 минут, очередь не растёт).

## Плюсы и минусы вариантов

### Таблица очереди в PostgreSQL

- Хорошо: постановка в той же транзакции
- Хорошо: нет нового компонента
- Плохо: пропускная способность ниже, чем у брокера

### Redis и BullMQ

- Хорошо: высокая скорость
- Плохо: постановка не атомарна с записью в БД
- Плохо: ещё один компонент

### RabbitMQ

- Хорошо: зрелый брокер
- Плохо: избыточен по нагрузке
- Плохо: ещё один компонент и его мониторинг

### Синхронный POST в обработчике вебхука

- Хорошо: проще всего
- Плохо: медленная цель замедляет приём
- Плохо: сбой теряет действие
