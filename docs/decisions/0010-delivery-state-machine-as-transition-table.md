# ADR-0010 Автомат доставки – таблица переходов, сверяемая с диаграммой

## Контекст и постановка проблемы

Доставка действия проходит 9 состояний (представление 016 SDD, `uml/models/state-delivery.puml`). Ошибка в переходах приводит к потере действия или к повторной команде на оборудование (BG-2, REQ-REL-002). Нужно реализовать автомат так, чтобы код и диаграмма не расходились.

## Драйверы решения

* корректность at-least-once (ADR-0006) и защиты от петель (ADR-0008);
* проверяемость: каждый переход покрыт тестом;
* диаграмма состояний – часть документации, которую читает Заказчик.

## Рассмотренные варианты

* чистая таблица переходов `TRANSITIONS` + тест, разбирающий `.puml`;
* библиотека XState;
* статус-флаги и условия в коде воркера.

## Результат решения

Выбрана **таблица переходов**: модуль `apps/api/src/modules/dispatcher/deliveryMachine.ts` содержит массив `{ from, event, guard?, to, action? }` и `COMPOSITE_TRANSITIONS` для переходов составного состояния «В обработке». Тест `deliveryMachine.test.ts` читает `state-delivery.puml`, раскрывает составное состояние (переход из него – из каждого подсостояния, переход в него – в начальное подсостояние) и сравнивает множество переходов с таблицей. Изменение диаграммы без кода (или наоборот) ломает сборку CI.

### Последствия

* Хорошо: диаграмма – исполнимая спецификация; модуль без зависимостей, тестируется за миллисекунды.
* Плохо: тест разбирает подмножество синтаксиса PlantUML (`a --> b : EVENT`), формат строк переходов зафиксирован.

## Плюсы и минусы вариантов

### XState
* Хорошо: визуализатор, иерархические состояния.
* Плохо: зависимость, своя нотация, расхождение с PlantUML всё равно нужно проверять.

### Флаги в коде воркера
* Хорошо: быстро написать.
* Плохо: недопустимые переходы не обнаруживаются; поведение нельзя сверить с диаграммой.
