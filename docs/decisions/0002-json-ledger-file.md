# Журнал в одном JSON-файле в каталоге пользователя

## Контекст и постановка задачи

Карточка автомобиля и расходы должны пережить закрытие программы (REQ-FUNC-007), лежать в каталоге текущего пользователя (REQ-SEC-002), не уходить в сеть (REQ-SEC-001) и не портиться, если пользователь ввёл недопустимое значение (REQ-REL-001, REQ-FUNC-008). Объём версии 0.1 — не больше 5 000 расходов, пересчёт сводки не дольше 1 секунды (REQ-PERF-001). Пользователь один.

Первая оценка исполнителя закладывала встроенную SQLite: схема, драйвер, миграция. Заказчик спросил, почему «просто запомнить чеки» занимает две недели. Вопрос, который остался после этого разговора: какое локальное хранилище закрывает те же требования короче по сроку?

Связанные требования: REQ-INT-003, REQ-FUNC-007, REQ-SEC-001, REQ-SEC-002, REQ-REL-001, REQ-REL-002, REQ-PERF-001, REQ-OBS-001.

## Драйверы решения

* Файл только внутри профиля пользователя.
* Неуспешная проверка ввода не меняет уже записанный файл.
* После штатного закрытия открывается последнее успешное состояние.
* 5 000 записей читаются и фильтруются быстрее 1 секунды на машине с 8 ГБ памяти.
* В журнал ошибок нельзя писать суммы и комментарии (REQ-OBS-001).
* Одна карточка автомобиля, одна валюта, фиксированные категории. Отдельный сервер базы не нужен.
* Срок: лишняя неделя на драйвер и схему не помещается в релиз 20.12.2026 без пользы для заказчика.

## Рассмотренные варианты

* Один JSON-файл, запись через временный файл и замену имени
* Встроенная SQLite
* Java-сериализация объекта в бинарный файл

## Итог решения

Выбранный вариант: «один JSON-файл, запись через временный файл и замену имени», потому что он выполняет требования к локальности и целостности и убирает неделю на схему и драйвер, которую заказчик справедливо не хотел оплачивать.

Каталог: `{user.home}/Avtouchet/ledger.json`. Запись идёт в `ledger.json.tmp` в том же каталоге. Файл журнала заменяется только после полной записи временного файла. Суммы в JSON — десятичные строки с двумя знаками (`"200.00"`), не двоичные дроби. В доменной модели та же сумма хранится целым числом копеек.

### Последствия

* Хорошо, потому что файл можно открыть блокнотом на защите и показать, что данные на месте и в каталоге пользователя.
* Хорошо, потому что обрыв записи оставляет предыдущий `ledger.json` нетронутым.
* Хорошо, потому что оценка хранения сжимается с двух недель до одной.
* Плохо, потому что весь журнал читается целиком. Для 5 000 строк это укладывается в REQ-PERF-001, для десятков тысяч — нет.
* Плохо, потому что два процесса «Автоучёта» одновременно могут затереть файл друг друга. Версия 0.1 этого не запрещает отдельным требованием; на защите запускаем один экземпляр.
* Нейтрально, потому что резервную копию пользователь может сделать сам, скопировав один файл.

### Подтверждение

Тест REQ-FUNC-007: расход и пробег на месте после нового запуска. Тест REQ-REL-001: отклонённая форма не меняет содержимое `ledger.json`. Осмотр пути: он внутри `user.home`. В тесте на 5 000 записей смена периода укладывается в 1 секунду.

## Плюсы и минусы вариантов

### Один JSON-файл, запись через временный файл и замену имени

Текст, одна карточка и массив расходов.

* Хорошо, потому что нет зависимости от нативного драйвера и нет миграций схемы.
* Хорошо, потому что атомарная замена имени файла закрывает REQ-REL-001 без транзакционного движка.
* Хорошо, потому что десятичная строка не накапливает ошибку двоичной дроби на суммах в BYN.
* Плохо, потому что запросы «только топливо за март» делаются в памяти, а не языком SQL. На заявленном объёме это приемлемо.

### Встроенная SQLite

Файл базы в том же каталоге пользователя, доступ через JDBC.

* Хорошо, потому что фильтр по дате и целостность транзакции — готовые свойства движка.
* Хорошо, потому что запас по объёму выше, чем у чтения всего JSON.
* Плохо, потому что драйвер, схема и отображение пяти категорий в таблицы занимают отдельную неделю. Заказчик этой недели в первой оценке не ожидал, а выигрыша для 5 000 строк она не даёт.
* Плохо, потому что на защите сложнее показать «вот запись» без инструмента просмотра базы.

### Java-сериализация объекта в бинарный файл

`ObjectOutputStream` в файл профиля.

* Хорошо, потому что пишется коротко.
* Плохо, потому что файл нельзя прочитать глазами и он ломается при смене полей класса между версиями программы.
* Плохо, потому что требование «неуспешная форма не портит файл» всё равно требует временного файла. Экономии против JSON почти нет.

## Дополнительная информация

Решение принято после первого раунда с заказчиком 06.11.2026. Исходная оценка «SQLite, 2 недели» снята. В плане остаётся 1 неделя на хранение внутри второго спринта.

Элементы SDD: VIEW-004, VIEW-007.
Пересмотр: если записей станет существенно больше 5 000 или появится вторая машина, хранение пересматривается отдельным ADR. До этого момента SQLite не подключаем «на вырост».
