# Модели динамического поведения — UML в текстовой нотации PlantUML

## Контекст и постановка задачи

В ЛР 3–4 структура и часть поведения описаны на SysML v2 с собственным рендером (`tools/sysml_render.py`,
`tools/sdd_render.py`). Для моделирования динамического поведения (ЛР 5) нужны диаграммы прецедентов с
`include`/`extend`/обобщением, активности с дорожками, ветвлениями, циклами и параллельными потоками,
состояний с составными состояниями и последовательности с фрагментами `alt`/`opt`/`par`. Каждая
диаграмма должна быть связана с прецедентом, требованиями и кодом. Как строить и хранить эти модели?

## Драйверы решения

* Модели должны храниться в Git как текст и проходить ревью в pull request (SRS 3.5.10).
* Полная нотация UML 2.5 для четырёх видов диаграмм, включая фрагменты и составные состояния.
* Трассируемость: прецедент → диаграммы → требования → код; проверка расхождений автоматически (SUP-S-03).
* Только бесплатные инструменты (CON-4); минимум ручной раскладки.

## Рассмотренные варианты

* PlantUML (текст `*.puml`, рендер `tools/uml_render.py`)
* Расширить собственный рендер SysML v2
* Mermaid
* Графический редактор (draw.io, StarUML)

## Итог решения

Выбранный вариант: «PlantUML», потому что он поддерживает все нужные конструкции UML с автоматической
раскладкой, хранится как текст и рекомендован заданием. SysML-модели ЛР 3–4 остаются (контекст, композиция,
данные, развёртывание); поведение 006 и 007 продублировано в UML с большей детализацией.

### Механизм построения

1. Источник — `uml/models/<вид>-<предмет>.puml`; вид: `usecase`, `activity`, `state`, `sequence`.
2. Изображения — `uml/img/<имя>.png`, строятся командой `python tools/uml_render.py`: локальный
   `plantuml.jar` (`PLANTUML_JAR`), свой сервер (`PLANTUML_SERVER`) или публичные Kroki / plantuml.com.
3. Изображения коммитятся вместе с моделью; `python tools/uml_render.py --check` показывает устаревшие PNG.

### Механизм связей

* Идентификаторы прецедентов `UC-NN` одинаковы в диаграмме, [`uml/use-cases.md`](../../uml/use-cases.md),
  SDD и тестах; бизнес-правила `BR-NN` — в [дополнительных спецификациях](../supplementary-specification.md).
* Каждый `.puml` начинается с комментария «Связи», где перечислены прецедент, потоки событий и
  связанные диаграммы. Таблица раздела 4 `use-cases.md` и представления SDD 013–018 замыкают трассировку.
* Шаги основного потока прецедента → действия диаграммы активности; альтернативные потоки → ветвления
  активности и фрагменты `alt` последовательности; линии жизни последовательности → компоненты SDD 002;
  состояния → значения `ScannerState` / `PassStatus` в коде.
* Для автомата сканера связь проверяется тестом (ADR-0010).

### Последствия

* Хорошо, потому что модели читаются в diff и правятся вместе с кодом.
* Хорошо, потому что раскладка автоматическая — добавление шага не требует перерисовки.
* Плохо, потому что для рендера нужна Java или сетевой сервер; PNG приходится коммитить.
* Нейтрально, потому что в проекте две нотации (SysML v2 для структуры, UML для поведения).

### Подтверждение

Все семь диаграмм строятся скриптом без ошибок; тест `apps/scanner/test/scannerMachine.test.ts`
сверяет диаграмму состояний с кодом; ревью pull request ветки `lab5`.

## Плюсы и минусы вариантов

### PlantUML

* Хорошо, потому что полная нотация UML и автоматическая раскладка.
* Плохо, потому что внешняя зависимость для рендера.

### Расширить собственный рендер SysML v2

* Хорошо, потому что одна нотация на проект.
* Плохо, потому что ручная раскладка координатами и около 20 ч на фрагменты, дорожки, составные состояния.

### Mermaid

* Хорошо, потому что GitHub отображает его без рендера.
* Плохо, потому что нет дорожек активности и `extend`/`include` в диаграммах прецедентов.

### Графический редактор

* Плохо, потому что бинарные файлы не ревьюятся в diff и расходятся с кодом.

## Дополнительная информация

Связанные решения: ADR-0010 (автомат сканера из диаграммы состояний). SDD 0.4, представления 013–018.
