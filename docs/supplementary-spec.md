# Дополнительные спецификации EasyTicket

Версия 0.1. Подготовил: Питковский В.В. Дата: 12.11.2026. Документ дополняет модель вариантов использования (`docs/use-cases.md`) требованиями, не привязанными к отдельным прецедентам. Источник: SRS `srs/srs.md`, раздел 3.3–3.5.

## 1. Функциональность (общие для всех прецедентов)

| ID | Требование | Прецеденты |
|----|------------|------------|
| SUP-FUNC-001 | Все ошибки пользовательского ввода сопровождаются понятным сообщением на русском языке | все |
| SUP-FUNC-002 | Служебные прецеденты (UC-08, UC-09, UC-10, UC-12) доступны только после входа (UC-11); права администратора и контролёра различаются | UC-08…UC-12 |
| SUP-FUNC-003 | Все изменения состояния мест, броней, заказов и билетов выполняются транзакционно | UC-03, UC-04, UC-07, UC-13 |

## 2. Удобство использования

| ID | Требование | Источник |
|----|------------|----------|
| SUP-USE-001 | Интерфейс корректно отображается на экранах от 320 px | REQ-INT-001…006 |
| SUP-USE-002 | Статус места передаётся не только цветом, но и подписью | SRS 3.1.1 |
| SUP-USE-003 | Соответствие WCAG 2.1 уровня AA | REQ-COMP-001 |
| SUP-USE-004 | Покупка выполняется без регистрации; число шагов от выбора места до подтверждения — не более 4 | SRS 2.4 |

## 3. Надёжность

| ID | Требование | Источник |
|----|------------|----------|
| SUP-REL-001 | При ошибке отправки письма — 3 повторные попытки с интервалом 1 минута | REQ-REL-001 |
| SUP-REL-002 | Если письмо не доставлено, билет доступен по номеру заказа и email | REQ-REL-002, UC-06 |
| SUP-REL-003 | Просроченные брони освобождаются автоматически, в том числе после перезапуска сервера | REQ-REL-003, UC-13 |
| SUP-REL-004 | Резервное копирование БД не реже одного раза в сутки | REQ-REL-004 |
| SUP-REL-005 | Доступность не менее 99 % времени в месяц, плановые работы — не более 2 часов в месяц (02:00–04:00) | REQ-AVAIL-001, 002 |

## 4. Производительность

| ID | Требование | Источник |
|----|------------|----------|
| SUP-PERF-001 | Главная страница загружается не дольше 2 секунд при скорости 10 Мбит/с | REQ-PERF-001 |
| SUP-PERF-002 | Время ответа API (95-й процентиль) до 500 мс при 100 одновременных запросах | REQ-PERF-002 |
| SUP-PERF-003 | Генерация QR-кода — не более 1 секунды на билет | REQ-PERF-003 |
| SUP-PERF-004 | Отправка письма асинхронная и не блокирует ответ покупателю; доставка в mock SMTP — не позднее 60 секунд после оплаты | REQ-PERF-004, REQ-FUNC-008 |

## 5. Безопасность

| ID | Требование | Источник |
|----|------------|----------|
| SUP-SEC-001 | При развёртывании вне локальной среды — HTTPS | REQ-SEC-001 |
| SUP-SEC-002 | QR-код подписан HMAC-SHA256; ключ хранится в переменной окружения, а не в репозитории | REQ-SEC-002, ADR-0003 |
| SUP-SEC-003 | Пароли сотрудников хранятся только в виде хеша с солью; после 5 неудачных попыток вход блокируется на 15 минут | REQ-SEC-003, REQ-FUNC-011 |
| SUP-SEC-004 | Защита от SQL-инъекций (параметризованные запросы) и XSS (экранирование вывода) | REQ-SEC-004 |
| SUP-SEC-005 | Email покупателя маскируется в журналах и доступен только по паре «номер заказа + email» | REQ-SEC-005 |
| SUP-SEC-006 | Бронирование защищено от гонок: одно место не может быть продано дважды | REQ-SEC-006, ADR-0002 |

## 6. Сопровождаемость и наблюдаемость

| ID | Требование | Источник |
|----|------------|----------|
| SUP-SUP-001 | Модульная структура и покрытие автоматическими тестами не менее 70 % | REQ-MAINT-001 |
| SUP-SUP-002 | Описание REST API публикуется в формате OpenAPI (Swagger UI) | REQ-MAINT-002 |
| SUP-SUP-003 | Ошибки журналируются с временем, контекстом запроса и идентификатором корреляции; журналы хранятся не менее 30 дней | REQ-OBS-001…003 |
| SUP-SUP-004 | Аудит служебных действий (вход, отмена брони, возвраты) | REQ-OBS-002 |

## 7. Ограничения проектирования и реализации

| ID | Ограничение | Источник |
|----|-------------|----------|
| SUP-CON-001 | Backend на Python, фреймворк FastAPI | ADR-0001 |
| SUP-CON-002 | База данных PostgreSQL | SRS 2.3 |
| SUP-CON-003 | QR-коды генерируются библиотекой qrcode, формат ISO/IEC 18004 | SRS 2.3, REQ-COMP-003 |
| SUP-CON-004 | В среде разработки письма отправляются через mock SMTP | SRS 2.3 |
| SUP-CON-005 | Запуск в Docker Compose на одном узле; параметры — переменные окружения | REQ-INST-001, REQ-DIST-001 |
| SUP-CON-006 | Все денежные суммы — в BYN | SRS 2.3 |

## 8. Нормативные документы

- WCAG 2.1 — доступность web-контента;
- RFC 5321, RFC 5322 — SMTP и формат писем;
- ISO/IEC 18004 — QR-коды;
- UML 2.5.1 — нотация диаграмм (ISO/IEC 19505).
