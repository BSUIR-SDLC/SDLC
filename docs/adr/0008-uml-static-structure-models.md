# Статическая структура описывается диаграммами UML классов, компонентов и развёртывания

## Контекст и постановка задачи

Структура FitSchedule в SDD 0.3 описана моделями SysML v2 (`docs/sdd/models`): модули и порты (002), таблицы
(003), узлы развёртывания (009). Представление 2.2.3 «Логическое» не было выделено — классы предполагалось
уточнять в коде. Для ЛР6 документацию нужно дополнить диаграммами UML классов, компонентов и развёртывания, а
перед началом реализации (I1, 08.02.2027) зафиксировать классы, которые будут созданы в модулях. Какие диаграммы
строить, на каком уровне детализации, и как связать их с моделями SysML v2, диаграммами поведения ЛР5 и кодом?

## Драйверы решения

* полная нотация UML 2.5 для статической структуры: классы с атрибутами и операциями, интерфейсы, все виды связей
  с кратностями; компоненты с портами, предоставляемыми и требуемыми интерфейсами, сборочными и делегирующими
  соединителями; узлы, среды выполнения, артефакты и манифестации;
* одна модель — одни имена: класс, компонент или узел называется так же, как модуль, таблица или контейнер в SDD
  и SysML v2, и как будущий пакет или класс в коде;
* текстовый исходник в Git рядом с документацией, проверка через pull request (REQ-MAINT-001);
* диаграммы читаются на листе А3 без масштабирования.

## Рассмотренные варианты

* три вида диаграмм UML (классы — на двух уровнях, компоненты, развёртывание) в PlantUML, изображения на листах А3;
* только SysML v2 (`part def`, `item def`, `allocate`) — продолжение моделей ЛР4;
* генерация диаграммы классов из кода (IntelliJ IDEA, ObjectAid) после реализации.

## Итог решения

Выбран вариант «три вида диаграмм UML в PlantUML», потому что он даёт нотацию, которой нет в бесплатных средствах
SysML v2 (порты с интерфейсами «шар–гнездо», артефакты и манифестации), продолжает ADR-0007 и позволяет
спроектировать классы до начала реализации, а не восстанавливать их из кода.

### Последствия

* Хорошо, потому что у SDD появилось логическое представление 014-class-model, а представления 002 и 009 получили
  UML-диаграммы, по которым Junior-разработчик получает задачи в I2 (классы и интерфейсы модуля).
* Хорошо, потому что диаграмма классов модуля `booking` прямо задаёт пакеты, интерфейсы и тесты (`BookingPolicyTest`),
  которые проверяются ArchUnit (ADR-0001).
* Плохо, потому что одна и та же структура описана дважды — SysML v2 и UML. Смягчение: таблица «Механизмы связи»
  ниже и правило ревью «изменил одну модель — обнови вторую».
* Плохо, потому что после начала реализации диаграммы классов могут разойтись с кодом. Смягчение: в I1 добавить
  тест ArchUnit на имена пакетов и зависимостей модулей, а диаграммы обновлять в том же pull request, что и код.

### Подтверждение

При ревью pull request проверяется, что: атрибуты сущностей на `class-domain` совпадают с `item def`
`data-model.sysml` и миграцией Flyway `V1__init.sql`; интерфейсы на `components` совпадают с `port def`
`architecture.sysml`; узлы и контейнеры на `deployment` совпадают с `docker-compose.yml`. После I1 зависимости
модулей проверяются тестом ArchUnit `ModuleDependencyTest`.

## Плюсы и минусы вариантов

### UML в PlantUML

* Хорошо, потому что поддерживает `interface`, `enum`, `abstract`, шаблоны `<T, ID>`, `port`, `portin`, `portout`,
  `artifact`, `node` и стереотипы.
* Хорошо, потому что совпадает с инструментом ЛР5 (ADR-0007), второй инструмент не нужен.
* Нейтрально, потому что раскладку больших диаграмм приходится уточнять вручную (изображения на листах А3).

### Только SysML v2

* Хорошо, потому что одна нотация со структурными моделями ЛР4.
* Плохо, потому что задание ЛР6 требует диаграмм UML, а у SysML v2 нет понятий «артефакт» и «манифестация».

### Генерация из кода

* Хорошо, потому что диаграмма всегда соответствует коду.
* Плохо, потому что код появится только в I1 (08.02.2027), а проектирование нужно сейчас; сгенерированные
  диаграммы показывают все поля и методы и плохо читаются.

## Дополнительная информация

### Механизмы построения диаграмм

1. **Диаграмма классов предметной области** (`class-domain`, уровень спецификации). Каждый `item def` модели данных
   SysML v2 (представление 003) стал классом сущности, каждый `enum def` — перечислением `«enumeration»`. Атрибуты
   записаны в формате `видимость имя : тип [кратность] = значение {ограничение}`: поля закрыты (`-`), ограничения
   `CHECK` таблиц перенесены в фигурные скобки, необязательные поля получили кратность `[0..1]`. Ссылочные поля
   (`ref`) заменены ассоциациями с именами ролей и кратностями по внешним ключам: `NOT NULL` → `1`, `NULL` → `0..1`,
   обратная сторона — `0..*`. Операции получены из событий диаграмм состояний ЛР5: переход `CONFIRMED → CANCELLED`
   стал операцией `Booking.cancel()`, `WAITING → PROMOTED` — `WaitlistEntry.promote()`. Вид связи выбран по
   времени жизни: элемент листа ожидания и история активности не существуют без занятия и пользователя —
   композиция; зал существует независимо от занятий — агрегация; остальные — ассоциации с направлением навигации от
   владельца внешнего ключа. Общее поведение «интервал времени» трёх сущностей вынесено в интерфейс `Scheduled`,
   который они реализуют.
2. **Диаграмма классов модуля** (`class-booking`, уровень реализации). Классы получены из линий жизни диаграмм
   последовательности ЛР5 (`:BookingController`, `:BookingService`, `:BookingPolicy`, `:BookingRepository`),
   операции — из их сообщений (`book()`, `check()`, `findByIdForUpdate()`, `promoteFirst()`). Типы операций:
   конструирующие (`BookingDecision.allow()`, `reject()`, `BookingDto.from()` — `{static}`), запросы без побочных
   эффектов (`overlaps()`, `isAllowed()` — `{query}`), модифицирующие (`book()`, `cancel()`) и закрытые служебные
   (`lockTraining()`). Порт модуля SysML v2 стал интерфейсом (`BookingApi`, `WaitlistApi`, `NotificationApi`),
   который реализует сервис; модуль обращается к другому только через интерфейс. Наследование показано для
   репозиториев (`JpaRepository<T, ID>` со связыванием `«bind»`) и иерархии исключений, каждое из которых
   соответствует ветке отказа на диаграммах активности ЛР5 и ответу 409/404 REST API.
3. **Диаграмма компонентов** (`components`). Компонент = модуль представления 002 (`part` в `FitScheduleApp`).
   Каждый `port def` стал предоставляемым интерфейсом («шар»); связь «использует» из `connect` — требуемым
   интерфейсом («гнездо») со сборочным соединителем либо зависимостью `«use»`. Внешние связи подсистемы
   `FitScheduleApp` проходят через порты `http`, `db`, `mgmt` с делегирующими соединителями к внутренним компонентам
   `api`, `persistence`, `ops`. Компонент `persistence` — инфраструктурный (`«infrastructure»`), бизнес-модулем не
   является.
4. **Диаграмма развёртывания** (`deployment`). Узлы взяты из `part deployment` модели `architecture.sysml` и
   представления 009: устройства (`«device»`) — устройство посетителя, учебный сервер, GitHub; среды выполнения
   (`«executionEnvironment»`) — браузер, Docker Engine; контейнеры Docker показаны вложенными узлами. Развёртываемые
   единицы — артефакты (`fitschedule.jar`, `spa-bundle`, `nginx.conf`, `backup.sh`), конфигурация — спецификации
   развёртывания (`application.yml`, `docker-compose.yml`, `.env`). Связи «канал связи» подписаны протоколом и
   портом. Отношение `allocate` SysML v2 выражено манифестацией: артефакт `fitschedule.jar` манифестирует компонент
   `FitScheduleApp`, `spa-bundle` — компонент `spa`.

### Механизмы связи между моделями

| Связь | Как обеспечивается |
|-------|--------------------|
| SysML `item def` → класс сущности | одинаковые имена (`Training`, `Booking`, `WaitlistEntry`…) и атрибуты; `enum def` → `«enumeration»` |
| Таблица БД → класс | атрибут = столбец, ограничение `CHECK` = `{…}`, внешний ключ = ассоциация с кратностью |
| Диаграмма состояний → класс | имя состояния = значение перечисления статуса, событие перехода = операция сущности или сервиса |
| Диаграмма последовательности → классы модуля | линия жизни = класс, сообщение = операция с теми же параметрами |
| Класс → компонент | класс лежит в пакете модуля (`booking.BookingService`), интерфейс модуля = предоставляемый интерфейс компонента |
| SysML `port def` / `connect` → компонент | порт = «шар» с тем же именем, `connect` = гнездо или `«use»` |
| Компонент → артефакт → узел | `«manifest»` (артефакт реализует компонент), артефакт вложен в узел-контейнер, на котором развёрнут |
| SysML `allocate` → развёртывание | `allocate fitSchedule to deployment.server.app` = `fitschedule.jar` в контейнере `app` |
| Диаграммы → SDD | представления 002, 009 и 014 ссылаются на `docs/uml/img/components.png`, `deployment.png`, `class-*.png` |
| Диаграммы → требования | примечания на диаграммах и столбец «Требования» таблиц SDD (REQ-INST-001, REQ-BUILD-001, REQ-REL-001…) |

Связи с решениями: композиция `BookingService ◆→ BookingPolicy` и интерфейсы модулей — ADR-0001;
`findByIdForUpdate` с `PESSIMISTIC_WRITE` — ADR-0004; `WaitlistApi.promoteFirst()` в транзакции отмены — ADR-0006;
`persistence` с Flyway и PostgreSQL 16 — ADR-0003.

Пересмотреть решение, если появится генератор, строящий UML из кода с нужной детализацией, или если
преподаватель потребует единый язык SysML v2.
