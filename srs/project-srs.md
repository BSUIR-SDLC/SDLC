## 1. Введение

### 1.1 Назначение документа

Документ описывает бизнес-требования к веб-приложению ApiPulse: что оно должно делать и зачем оно нужно заказчику. Документ предназначен для заказчика (согласование требований), разработчика (реализация) и тестировщика (проверка). Документ определяет **ЧТО** должна делать система, а не **КАК** она будет устроена.

### 1.2 Область применения продукта

**Продукт:** ApiPulse, версия 1.0 (рабочее название).

**Назначение.** Мониторинг доступности внешних API-сервисов и контроль затрат на их использование.

**Бизнес-цели:** будут уточнены с заказчиком.

**Границы первой версии (предварительно):**

* входит: проверка доступности API, учёт расходов и бюджет, уведомления, вход пользователя;
* не входит: оплата счетов поставщикам, управление самими API, автоматический сбор расходов у поставщиков, мобильное приложение.

### 1.3 Определения, акронимы и сокращения

| Термин | Определение |
|--------|-------------|
| API | Application Programming Interface — интерфейс, через который одна программа обращается к другой |
| Эндпоинт | Конкретный адрес API, к которому отправляется запрос |
| HTTP-код | Число в ответе сервера: 200 — успех, 4xx — ошибка запроса, 5xx — ошибка сервера |
| Бюджет | Максимальная сумма, которую пользователь готов потратить на API за месяц |
| SRS | Software Requirements Specification — спецификация требований к ПО |
| UI | User Interface — пользовательский интерфейс |
| CSV | Текстовый формат таблицы, в котором значения разделены запятыми |

## 2. Обзор продукта

### 2.1 Перспектива продукта

ApiPulse — самостоятельное веб-приложение (новый продукт). Работает в браузере пользователя, отправляет HTTP(S)-запросы на адреса API, которые указал пользователь, и отправляет уведомления на электронную почту. Проверяемые API не изменяет.

### 2.2 Функции продукта

* Добавление и удаление проверяемых API.
* Автоматическая регулярная проверка доступности каждого API.
* Отображение статуса всех API на одной панели.
* Уведомление пользователя о недоступности API.

Остальные функции (учёт расходов, бюджет, вход пользователей) будут добавлены после согласования.

### 2.3 Ограничения продукта

* Веб-приложение, доступное через современные браузеры.
* Язык разработки: Java.
* Язык интерфейса и документации: русский.

### 2.4 Характеристики пользователей

* **Разработчик:** добавляет API и следит за их состоянием, работает с приложением ежедневно.
* **Руководитель команды:** смотрит общую картину, заходит редко и не обязан разбираться в технических деталях.

### 2.5 Допущения и зависимости

* **Допущение:** проверяемые API доступны из интернета, для проверки достаточно одного HTTP-запроса.
* **Зависимость:** для отправки писем нужен почтовый сервис.

### 2.6 Распределение требований

Все требования этого документа относятся к первой версии (1.0).

### 3.2 Функциональные требования

* **ID:** REQ-FUNC-001
* **Название:** Добавление проверяемого API
* **Формулировка:** Система должна позволять пользователю добавить API, указав название, адрес эндпоинта и интервал проверки, а также удалить ранее добавленный API.
* **Обоснование:** Без списка API нечего проверять.
* **Критерии приёмки:** После сохранения API появляется на главной панели; пустое название и некорректный адрес отклоняются с понятным сообщением; после удаления API исчезает с панели.
* **Метод верификации:** Test

* **ID:** REQ-FUNC-002
* **Название:** Периодическая проверка доступности
* **Формулировка:** Система должна автоматически проверять каждый добавленный API с интервалом, заданным пользователем, в диапазоне от 1 до 60 минут (по умолчанию 5 минут). API считается недоступным, если ответ не получен за 10 секунд либо получен HTTP-код 5xx.
* **Обоснование:** Заказчик хочет узнавать о сбое раньше своих клиентов.
* **Критерии приёмки:** Следующая проверка происходит через заданный интервал; значения интервала вне диапазона отклоняются; недоступный эндпоинт получает статус «недоступен».
* **Метод верификации:** Test

* **ID:** REQ-FUNC-003
* **Название:** Главная панель статусов
* **Формулировка:** Система должна отображать на главной панели для каждого API текущий статус (работает / недоступен), время последней проверки и время ответа.
* **Обоснование:** Состояние всех сервисов должно быть видно с одного экрана.
* **Критерии приёмки:** Данные на панели соответствуют результату последней проверки; панель обновляется без перезагрузки страницы.
* **Метод верификации:** Test

* **ID:** REQ-FUNC-004
* **Название:** Уведомление о недоступности API
* **Формулировка:** Система должна уведомлять пользователя на экране и по электронной почте о недоступности API после трёх неуспешных проверок подряд, не позднее чем через одну минуту после третьей, а также уведомлять о возобновлении работы.
* **Обоснование:** Три проверки подряд защищают от ложных тревог из-за кратковременных сбоев сети.
* **Критерии приёмки:** После третьей подряд неуспешной проверки создаётся ровно одно уведомление; пока API недоступен, повторные уведомления не создаются; после первой успешной проверки отправляется уведомление о восстановлении; если почта недоступна, уведомление остаётся на экране.
* **Метод верификации:** Test
